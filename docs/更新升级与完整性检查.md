# 更新升级与完整性检查文档

面向**已经部署好**的站点：怎么升级、升级前怎么检查、升级后怎么验证、
以及出错怎么退回。命令行部署与宝塔面板部署都覆盖。

---

## 零、后台自带「检查更新」

不用去 GitHub 手动翻版本 —— 登录后台 → **总览** → 「运行配置」的 **系统版本**
那一行，点 **检查更新** 即可。

```
总览 → 运行配置
  系统版本   v1.0.2    [检查更新] [强制]   已是最新版本 v1.0.2
```

- **发现新版本**时会展开一张卡片：新版本号、发布日期、来源（GitHub Release
  或仓库 VERSION 文件）、发布说明全文，以及一个跳转到 GitHub 的链接。
- **强制**：忽略缓存，立刻回源重查。
- **检查更新失败**时会明确显示失败原因（网络不通 / 无权限 / 速率限制），
  **绝不会**伪装成「已是最新」—— 那会让你错过安全更新。

### 配置项（站点设置 → 程序更新）

| 键 | 默认 | 说明 |
|---|---|---|
| `update.enabled` | 开 | 关掉则后台不显示检查入口 |
| `update.repo` | `2016xyz/kwrt-clone` | 更新源仓库（owner/repo） |
| `update.ref` | `main` | 仓库没有 Release 时，从哪个分支读 `VERSION` 文件 |
| `update.token` | 空 | 私有仓库必填；留空回落到「GitHub 构建」的 Token |
| `update.include_prerelease` | 关 | 开启后 `-beta` / `-rc` 也算可用更新 |
| `update.cache_minutes` | 10 | 检查结果缓存时长 |

> **为什么要缓存**：GitHub 未认证请求每小时只有 60 次。不加缓存的话，
> 反复点几下就会把限额打满，**连固件构建派发一起挂掉**。
> 缓存与配置绑定：改了仓库或预发布开关，旧缓存立即作废，不会拿别的仓库的
> 结论误导你。

### 两种更新源的优先级

1. **GitHub Release**（推荐）：`/repos/<repo>/releases` 里最新的那条非草稿
   发布，能拿到发布说明与页面链接。
2. **仓库里的 `VERSION` 文件**：仓库还没打过 Release 时，读 `update.ref`
   分支上的 `VERSION` 文件。

### 检查到新版本之后

后台**只做检查，不会替你升级** —— 让一个网页按钮去覆盖正在运行的程序文件
并重启自身，一旦中途出错就没人收得了场。按下面的备份 → 拉取 → 重启流程手工做。

## 一、升级前：先做这三件事

### 1. 备份（不可跳过）

```bash
cd /www/wwwroot/kwrt            # 换成你的站点目录

# ① 数据库
#   SQLite：
cp users.db users.db.bak-$(date +%F-%H%M)
#   MySQL：
mysqldump -h127.0.0.1 -ukwrt -p'口令' --single-transaction kwrt > kwrt-$(date +%F-%H%M).sql

# ② 运行数据（构建产物、上传、缓存）
tar czf store-$(date +%F-%H%M).tgz store/ data/ cache/ 2>/dev/null

# ③ 配置
cp config.local.json config.local.json.bak 2>/dev/null
```

宝塔用户：**计划任务 → 备份数据库/站点目录** 也可以，但升级前手动做一次更稳妥。

### 2. 看清当前版本

```bash
cat VERSION                     # 例如 1.0.2
```

或浏览器访问 `https://你的域名/healthz`，看 `"version"` 字段。
后台控制台页头也会显示版本徽标。

### 3. 记下当前状态基线（用于升级后对比）

```bash
# 数据量基线
#   SQLite：
sqlite3 users.db "SELECT 'users',COUNT(*) FROM users UNION ALL SELECT 'builds',COUNT(*) FROM builds;"
#   MySQL：
mysql -h127.0.0.1 -ukwrt -p'口令' kwrt -e \
  "SELECT 'users',COUNT(*) FROM users UNION ALL SELECT 'builds',COUNT(*) FROM builds;"

# 站点自检
curl -s https://你的域名/healthz
```

## 二、升级方式

### 方式 A：一键脚本（推荐）

```bash
cd /www/wwwroot/kwrt
sudo ./update.sh
```

脚本做四件事：

1. `git pull` 拉取新代码（有未提交改动会先提示，不会硬拉）
2. 按 `requirements.txt` 更新依赖
3. **重启服务**
4. 提示「运行时数据（users.db / store/ / data/ / kwrt.env）未被改动」

参数：

| 参数 | 作用 |
|---|---|
| `--no-pull` | 跳过 `git pull`（代码已手动更新时用） |
| `SKIP_RESTART=1 ./update.sh` | 只更新代码不动服务 |

**服务缺失时脚本会自动装上**（含 `systemctl enable` 开机自启），
不再只打印一句「请手动重启」—— 这是 1.0.1 修掉的问题。

### 方式 B：手动（宝塔用户常用）

```bash
cd /www/wwwroot/kwrt
git pull                      # 或从面板「文件」上传覆盖
php php/scripts/gen_settings_schema.py    # 若 settings 结构有变，同步 PHP 侧
# 宝塔：软件商店 → PHP → 重载配置（改过 php.ini/环境变量时）
```

> 宝塔用户注意：若你通过 PHP-FPM 的 `env[...]` 配置了数据库，
> 升级**不会**动那部分；但若你改过 `php-fpm.d/www.conf`，重载一次更保险。

### 方式 C：PHP 版专有 —— 数据库结构更新

PHP 版启动时会**自动跑幂等迁移**（`Db::migrate()`）：新增的表会建，
已有的表不动。所以正常升级**不需要**手工执行任何 SQL。

若你想提前确认（尤其是 MySQL），可手工触发一次：

```bash
# SQLite
php -r 'require "php/src/helpers.php";
spl_autoload_register(function($c){if(!str_starts_with($c,"Kwrt\\"))return;
 $f="php/src/".str_replace("\\","/",substr($c,5)).".php";if(is_file($f))require $f;});
Kwrt\Db::pdo(); echo "迁移完成\n";'

# MySQL（带环境变量）
KWRT_DB_DRIVER=mysql KWRT_MYSQL_DB=kwrt KWRT_MYSQL_USER=kwrt KWRT_MYSQL_PASS='口令' \
  php -r '...同上...'
```

## 三、升级后：必跑的检查

### 1. 服务与版本

```bash
curl -s https://你的域名/healthz
```

期望：`"ok":true`，且 `"version"` 是新的版本号。

### 2. 数据库连通与数据完好

```bash
# 数据量应与升级前的基线一致（或更多）
mysql -h127.0.0.1 -ukwrt -p'口令' kwrt -e "SELECT COUNT(*) FROM users;"
# 或 SQLite: sqlite3 users.db "SELECT COUNT(*) FROM users;"
```

### 3. 页面路由

```bash
for p in / /packages/ /newpkg/ /fadian/ /contact/ /login/ \
         /healthz /api/v1/site /robots.txt /sitemap.xml /manifest.webmanifest; do
  printf "%-28s %s\n" "$p" "$(curl -s -o /dev/null -w '%{http_code}' https://你的域名$p)"
done
```

除 `/index.css` 等历史路径应为 **301** 外，其余都应是 **200**。

### 4. 后台功能抽查

登录后台，逐个点一遍：
总览 / 用户 / 构建队列 / 产物 / 设置中心 / 邮件 / 支付 / 赞助 / 公告…

**重点看「设置中心」能否保存**：如果改了不生效，几乎一定是数据库连接问题
（连到了另一个库，或 PHP-FPM 环境变量没生效）。

### 5. 仓库自带的完整性检查（若你拿到的是完整仓库）

```bash
python3 tools/verify_integrity.py      # 22 项：语法/完整性/自洽/对称/交付
bash    tools/verify_launcher.sh       # 11 项：启动脚本
python3 tools/verify_round6.py         # 42 项：版本/systemd/验证码/多队列
python3 tools/verify_php.py            # 26 项：PHP 侧功能与 schema 同源
python3 php/scripts/gen_settings_schema.py --check   # 设置 schema 两版同源
python3 php/scripts/gen_mysql_schema.py --check      # MySQL DDL 与 SQLite 同源
python3 tools/verify_installer.py                     # 22 项：安装向导全流程 + 安全边界
python3 tools/verify_audit_fixes.py                   # 14 项：构建队列可靠性 + 路径守卫（隔离副本内跑）
python3 tools/verify_php_compat.py                    # 6 项：PHP 版本守卫 + 真 PHP 7.4 容器解析/实跑
python3 tools/verify_setting_parity.py                # 4 项：无「后台能改、代码不读」的静默失效设置项
python3 tools/verify_remote_backend.py                # 10 项：远端后端/外链下载/自定义邮件模板（离线）
python3 tools/verify_remote_backend.py --dispatch     # 11 项：额外做**真实**GitHub 派发（用后即删 run）
python3 tools/verify_mysql.py                         # 11 项：MySQL 支持（无库时自动跳过）
```

> 需要 Python 3.9+ 与 `php` CLI。**这些检查是只读的**，
> 会跑在临时库上，不会碰你的生产数据。

## 四、升级后版本号显示不对？

版本号的**唯一真源是仓库根的 `VERSION` 文件**：

- Python 读 `app/version.py` 里的 `VERSION` 常量
- PHP 读仓库根 `VERSION` 文件

若两边显示不一致，说明 `app/version.py` 与 `VERSION` 文件被改得不同步了。
`tools/verify_round6.py` 的 V-1 / V-4 会断言这一点。

**发版流程**：改 `VERSION` 文件 + 同步 `app/version.py` 的常量，两版同时生效。

## 五、回滚

```bash
cd /www/wwwroot/kwrt
git log --oneline -5           # 找到上一个正常版本
git checkout <上一个 commit>   # 或 git reset --hard <commit>

# 恢复数据（只有结构变更出问题时才需要）
cp users.db.bak-<时间戳> users.db
# 或 MySQL： mysql -ukwrt -p'口令' kwrt < kwrt-<时间戳>.sql

sudo systemctl restart kwrt    # 或宝塔重载 PHP
```

**注意**：回滚代码**不会**回滚数据库。若新版做过结构变更（新增表/字段），
旧版代码通常仍能跑（旧代码只是不认识新表）；反之新版能识别旧结构。
真正危险的是**用旧备份覆盖新数据** —— 会丢掉升级后产生的订单和构建记录，
所以只在确认数据损坏时才那样做。

## 六、MySQL 特有的升级注意

1. **库/表与 SQLite 不同步**：SQLite 是单文件，与代码同目录；
   MySQL 在服务里。改代码目录**不会**影响 MySQL 数据 —— 这点更安全。
2. **DDL 同源**：MySQL 建表语句由脚本从 SQLite 真源派生
   （`php/scripts/gen_mysql_schema.py`）。改表结构时：
   ```bash
   # ① 改 php/src/Schema.php 的 SQLITE
   # ② 重新生成 MySQL
   python3 php/scripts/gen_mysql_schema.py
   # ③ 确认两者同步
   python3 php/scripts/gen_mysql_schema.py --check
   ```
   **不要手改生成的 `MYSQL` 常量** —— 下次生成会被覆盖。
3. **幂等迁移**：新增表自动建；**已有表加字段不会自动改**。
   加字段需要你自己执行 `ALTER TABLE`（这是刻意的：
   自动 ALTER 在生产库上风险太大）。
4. **口令没变就别动**：`KWRT_MYSQL_*` 环境变量改了之后要**重载 PHP-FPM**，
   否则不生效 —— 这是「改完没反应」的头号原因。

## 七、一键自检脚本

把下面存成 `check.sh` 放在站点目录旁，升级后跑一次：

```bash
#!/usr/bin/env bash
# 用法: ./check.sh https://你的域名
set -u
BASE="${1:-http://127.0.0.1:8080}"
echo "== 版本 =="
curl -s "$BASE/healthz" | grep -o '"version":"[^"]*"'
echo "== 路由 =="
for p in / /packages/ /newpkg/ /fadian/ /contact/ /login/ \
         /healthz /api/v1/site /robots.txt /sitemap.xml; do
  printf "  %-26s %s\n" "$p" "$(curl -s -o /dev/null -w '%{http_code}' "$BASE$p")"
done
echo "== 设置读写（应能读到刚写的值）=="
curl -s "$BASE/api/v1/site" >/dev/null && echo "  /api/v1/site OK"
echo "== 数据库 =="
if [ -f users.db ]; then
  echo "  SQLite users=$(sqlite3 users.db 'SELECT COUNT(*) FROM users;' 2>/dev/null)"
else
  echo "  MySQL：请用 mysql 客户端核对（见文档 §三.2）"
fi
```

## 八、故障速查

| 现象 | 原因 | 处理 |
|---|---|---|
| 整站白屏，报 `Dynamic class names are not allowed in compile-time ::class fetch` | 服务器 PHP 是 7.x | 宝塔 → 网站 → 设置 → PHP 版本改 8.0+。详见《宝塔面板部署指南》§零 |
| 打开 `/install.php` 说「向导已锁定」 | 正常 —— 站点已安装 | 要重装见《宝塔面板部署指南》§五 |
| 打开 `/install.php` 说「检测到已存在的站点」 | 库里有管理员但没有锁文件 | 放空文件 `data/install.allow` 再刷新 |
| 升级后 `/healthz` 不通 | 服务没起来 | `journalctl -u kwrt -n 100 --no-pager`（宝塔：PHP-FPM 日志） |
| 版本号没变 | 代码没真正更新 / 缓存 | 确认 `git log -1`；PHP 若开 opcache 则重载 FPM |
| 后台改设置不生效 | 连到了另一个库 | 比对 `/healthz` 与 CLI 的库名；重载 FPM |
| 整站 404 | 伪静态丢了 | 宝塔 → 站点 → 伪静态，重新粘贴 `try_files` |
| 中文变问号 | 库不是 utf8mb4 | 见《宝塔面板部署指南》§九 |
| 构建一直排队 | FPM/Nginx 超时 | 见《宝塔面板部署指南》§七.3 |
| `Unknown database` | 库没建 | 按报错里给的那条 `CREATE DATABASE` 执行 |
| 升级后数据变少 | 误用旧备份覆盖 | 立即停站，从最新备份恢复；核对基线数字 |
