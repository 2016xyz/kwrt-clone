## 一、事故：支付二维码必然 500

### 1.1 现象与取证

用户报告后，用**真实登录 + 真实订单**在线上复现（未新建订单，取用既有订单）：

```http
GET /api/v1/sponsor/pay/XSP17904765955c9ce29b/qr.png HTTP/1.1
Host: op.2016xlx.cn
User-Agent: Mozilla/5.0
Cookie: kwrt_session=***
```

```http
HTTP/1.1 500 Internal Server Error
Content-Type: text/plain; charset=utf-8
Content-Length: 21

Internal Server Error
```

服务端（`journalctl -u kwrt`）取得完整栈底：

```
File "/root/kwrt-clone/app/main.py", line 2259, in sponsor_pay_qr
    png = pay.qr_png_bytes(d["qr_code"])
File "/root/kwrt-clone/app/pay.py", line 385, in qr_png_bytes
    img = img.resize((size, size))
ModuleNotFoundError: No module named 'PIL'
```

> 同一异常在 **10:31 / 10:36 / 10:36 / 10:38** 各出现一次 —— 用户已反复撞上。

### 1.2 根因

**不是「服务器少装了一个包」，而是代码使用的依赖没有写进 `requirements.txt`。**

`app/pay.py` 的 `qr_png_bytes()` 用的是 `qrcode` 的**默认图像工厂**（即 PIL 实现），
末尾还调了 `img.resize()`。而 `requirements.txt` 里只声明了 `qrcode`，并且**注释明确写着**：

```
# 支付二维码渲染为内联 SVG（app/pay.py:qr_svg_data_uri）
# 使用 qrcode.image.svg，**不需要 Pillow**（避免引入图像库攻击面）
qrcode>=7.4,<9.0
```

于是形成一条完美的自欺链：

| 环节 | 表现 |
|---|---|
| 注释 | 声称不需要 Pillow |
| 开发机 | 恰好装着 Pillow（被别的项目带来的）→ 本地全绿 |
| 干净部署 | 按 requirements 装 → **必然** `ModuleNotFoundError` |
| 用户可见 | 前端支付弹窗的 `<img>` 正指向该端点 → **支付二维码永远出不来** |

`web/assets/js/app.js` 与 `web/assets/js/login.js` 都把 `<img src>` 指向
`/api/v1/sponsor/pay/{out_trade_no}/qr.png`，所以这不是一个「边缘接口」，是支付主路径。

**缺陷类别：注释承诺的能力 ≠ 代码实际依赖的能力。**

### 1.3 修法（并说明为什么不装 Pillow）

摆在前面的有两条路，选了第二条：

| 方案 | 评价 |
|---|---|
| A. 装上 Pillow + 写进 requirements | 把一个**体积大、C 扩展、CVE 频发**的库引入生产，只为画一张二维码；且违背项目自己写下的「避免引入图像库攻击面」的决策 |
| B. **去掉这个依赖** | PNG 是公开格式，1 bit 调色板图只需 `zlib + struct` 即可拼出。约 40 行，零依赖，可断言 |

选 B。顺带修掉一个**未被发现的隐性缺陷**：原先的 `resize()` 走重采样，
会把 QR 模块边缘抹糊。QR 必须用**最近邻整数倍**放大，否则模块错位——
所以新实现宁可边长少几个像素（297 而不是 320），也不做非整数缩放。

```python
# app/pay.py（新）
def qr_png_bytes(text: str, size: int = 320) -> bytes:
    import zlib, qrcode
    q = qrcode.QRCode(box_size=1, border=2,
                      error_correction=qrcode.constants.ERROR_CORRECT_M)
    q.add_data(text); q.make(fit=True)
    m = q.get_matrix(); n = len(m)
    scale = max(1, int(size) // n)      # 最近邻整数倍
    dim = n * scale
    raw = bytearray(); rowbytes = (dim + 7) // 8
    for y in range(dim):
        src = m[y // scale]; raw.append(0)      # filter type 0
        line = bytearray(rowbytes)
        for x in range(dim):
            if not src[x // scale]:             # 浅色 -> 调色板索引 1
                line[x >> 3] |= 0x80 >> (x & 7)
        raw += line
    return (_PNG_SIG
            + _png_chunk(b"IHDR", _pc_ihdr(dim, dim))
            + _png_chunk(b"PLTE", bytes((0x0F,0x17,0x2A, 0xFF,0xFF,0xFF)))
            + _png_chunk(b"IDAT", zlib.compress(bytes(raw), 9))
            + _png_chunk(b"IEND", b""))
```

### 1.4 闭环验证（三层，全部可真跑）

**① 位图级**：把生成的 PNG 的 IDAT 解压还原成像素矩阵，与 `qrcode` 库的矩阵**逐像素比对**。

```

```

**② 真实解码器级**：用 OpenCV 的 `QRCodeDetector` 解出来，内容必须一致。

```

```

**③ 线上生产级**：把**线上真实返回的** PNG 下载下来再解码。

### 1.5 根因级护栏（这类缺陷不该再出现第二次）

只修一个函数不够 —— 「代码用了 X，requirements 没写 X」是一**类**缺陷。
补两条常驻护栏：

| 工具 | 断言 | 结果 |
|---|---|---|
| `tools/verify_qr_png.py` | PNG 结构/CRC/IHDR/位图逐像素等于库矩阵 + OpenCV 真解码 + **静态护栏** + **负向对照（注入 PIL 写法后护栏必须变红）** | **9/9 ✓** |
| `tools/verify_declared_deps.py` | ① app/ 里每个第三方 import 都在 requirements.txt 中声明；② **建一个全新 venv、只装 requirements.txt**，再把 `app/` 全量导入并实跑二维码生成；③ 断言该环境确实没有 Pillow | **5/5 ✓** |

第二条是关键：静态扫描 import 看不见 `python-multipart`、`jinja2` 这类
「不被按名导入却是 FastAPI 运行时必需」的包；只有**真的建一个干净环境跑一遍**才测得出来。

```
D-2  干净 venv 可导入 app/ 全部模块           ✓  失败 0 个
D-3  干净环境里二维码生成可用                  ✓  PNG 559 字节 / SVG 8518 字符
D-4  干净环境确实没有 Pillow（证明不是碰巧）      ✓  无 Pillow
```

| `app/templates/mail/reset.html` | 重置邮件正文（琥珀色，与注册验证的蓝色刻意区分） |
| `web/reset.html` | 页面：申请 / 已发送 / 设新密码 / 失效 / 完成 五态 |
| `app/main.py` | `GET /reset/` + `POST /api/v1/reset_request｜reset_check｜reset_confirm` |
| `web/login.html` + `assets/js/login.js` | 登录页「忘记密码」入口（受 `page.reset_enabled` 控制） |
| `app/sitesettings.py` | 新增 `mail.reset_ttl_hours` / `mail.reset_subject` / `mail.reset_body` / `page.reset_enabled` / `security.captcha_on_reset` |

### 2.2 设计要点（每条都有具体理由）

**① 反枚举 —— 账号存在与否，对外必须不可区分**

```
账号不存在          -> 200 {"status":"ok","message": RESET_REPLY}
未登记邮箱          -> 200 {"status":"ok","message": RESET_REPLY}
账号已停用          -> 200 {"status":"ok","message": RESET_REPLY}
冷却中（60 秒内）    -> 200 {"status":"ok","message": RESET_REPLY}   ★ 静默跳过发送
真正发出了          -> 200 {"status":"ok","message": RESET_REPLY}
```

`RESET_REPLY` = 「如果该账号存在且已绑定邮箱，重置邮件已经发出，请查收（含垃圾邮件目录）。」

差异只写进审计日志。**特别地，冷却不能返回 429** —— 否则「该账号存在且刚申请过」
与「账号不存在」就可区分，等于免费送出一个用户枚举接口。

**② 站点级失败可以明说**

SMTP 没配置时返回 `503 本站邮件服务尚未配置`。这对**任何账号都一样**，不构成枚举面；
反过来若静默返回成功，用户会一直等一封永远不来的信。

**③ 验证码优先，且默认开**

`reset_request` 会真实发信 —— 没有验证码，遍历用户名就是一台现成的邮件轰炸放大器。
新增独立开关 `security.captcha_on_reset`，**默认 true**，在任何查询与发信之前校验。

**④ 改密 = 踢下线**

成功后依次：注销该账号**全部会话** → 作废其余找回令牌 → 作废未用的邮箱验证令牌
→ 清掉登录失败锁定计数。否则被盗号者只要不刷新就能继续用旧会话。

**⑤ 令牌先原子消费，再改口令**

```sql
UPDATE password_resets SET used=1, used_at=? WHERE token_hash=? AND used=0
```

条件写在 UPDATE 里、靠 `rowcount` 定归属。并发点两下同一链接时只有一方拿到 1，
另一方得到明确提示 —— 而不是「两边都改了口令」。

### 2.3 顺带修掉一个真实 DoS

`app/verify.py` 的 `_db()` 返回**原生 `sqlite3.Connection`**，而它的上下文管理器
**只 commit/rollback、从不 close**；连接又处在引用环里，要等分代 GC 才回收。

实测（禁用 GC）：

```
verify.py 原生连接     300 次调用  ->  泄漏 1200 个 fd（约 4 个/次）
dbutil.ClosingConnection 300 次调用 ->  泄漏 0 个 fd
```

默认 `ulimit -n 1024` 下，约 **256 次请求即 fd 耗尽** → 进程级 DoS。
已改为 `factory=dbutil.ClosingConnection`。

## 三、PHP 侧对齐（并揪出同一处缺陷）

| `php/src/Mailer.php` | `+ sendReset()`：走后台可改的 `mail.reset_subject` / `mail.reset_body`；琥珀色 |
| `php/src/Controllers/AuthController.php` | `+ resetPage / resetRequest / resetCheck / resetConfirm` |

### 3.1 顺带修掉的真缺陷：`/api/v1/captcha` 门禁漏判

```php
// 修前（php/src/Controllers/ApiController.php）
if (!Captcha::enabled() && !Captcha::enabledForRegister()) {
    json_out([... '验证码未启用'], 404);
}
```

漏了 `enabledForReset()`。后果：**只开 `security.captcha_on_reset`** 的部署
（也就是本功能的默认配置）下，`/api/v1/captcha` 返回 404 → 找回页取不到验证码
→ **整个找回流程在 PHP 版完全不可用**。

Python 版同一个位置犯过同样的错，本轮一并修掉（线上已验证 `HTTP 200`）。

> 这个缺陷单看 PHP 代码「逻辑自洽」，**只有把两版都跑起来才发现**。

## 四、如实记录：一处既有差异（本次未改）

测试按**语义**断言而非照抄某一版的字面量。

> 记这一条的理由：把它写下来，比悄悄让测试绕过它更诚实；也便于将来真要统一时有据可查。

| SMTP 账号 | 通常是完整邮箱 | `noreply@your-domain` |
| SMTP 密码/授权码 | **不是登录密码**，是服务商的授权码 | —— |
