## 一、总体结论

**总体风险等级：高危**（修复前）→ **低危**（修复后）

理由：本轮发现 1 个**进程级拒绝服务**（SQLite 连接不关闭导致 fd 线性泄漏）和
1 个**任意文件写入**（构建依赖索引里的文件名未归一化），两者都不是理论问题，都有实测复现。
其余为崩溃类与纵深防御类问题。

**最优先修复项（按危害排序）**

1. **`with db() as c:` 只提交不关闭 → fd 线性泄漏 → 进程级 DoS**
   实测 **1 次调用泄漏 1 个 fd**，2000 次调用泄漏 2000 个。
   默认 `ulimit -n = 1024` 的机器上，几百次请求即可让整个进程再也打不开任何文件。
2. **构建依赖索引的 `Filename` 未归一化 → 任意文件写入**
   把索引里的 `Filename` 写成 `../../../../tmp/x.ipk`，实测**文件真的落到了下载目录之外**。
   索引来自上游（`dl.openwrt.ai` 与 ImageBuilder 的 `repositories.conf`），属供应链投毒面。
3. **数值配置项对 `1e400`/`nan` 抛未捕获的 `OverflowError` → 500**
   `_enc` / `_dec` / `validate` 三处都只捕获 `(TypeError, ValueError)`。

**是否建议上线：建议上线（附条件）**

上述 1、2、3 已在本次提交中修复并逐项实测通过（`tools/verify_round5.py` 13/13）。
上线前建议补充两件事：**确认部署是单进程还是多 worker**、**给 systemd 设置
`LimitNOFILE`**（见文末「需要我补充的信息」）。

## 四、本轮的功能改造（用户要求的三项）

不属于漏洞，但属本次交付内容，一并说明并附验证。

### 4.1 后台可删除本地构建物

**问题**：原先只有「按构建记录删除」与「清空全部」两个动作，管理端
**看不见**每个构建占多少盘，也看不到「DB 里记录已不存在、目录还在」的**孤儿目录**
（重启或历史清理后常见，会一直占盘且不在任何列表里）。

**实现**

- 新增 `app/artifacts.py`（261 行）：`scan()` 盘点 / `delete()` 单删 /
  `delete_orphans()` 清孤儿 / `purge_all()` 全清 / `uploads_scan()` 只读展示
- 新增端点：`GET /api/v1/admin/artifacts`、`POST /api/v1/admin/artifact`
  （`action = delete | delete_record | delete_orphans`）
- 管理台「队列与存储」新增「本地构建物」面板：占用 / 文件数 / 属主 / 时间 /
  **孤儿标记**，按占用从大到小排列；支持「删除产物（保留记录）」与
  「连记录删除」；顶部可一键**清理孤儿目录**
- **删产物同时作废相关下载令牌**（原先会留下指向已删文件的悬空限时链接）
- `purge_store` 收口到 `artifacts.purge_all()`，同样作废全部令牌
- 构建列表新增 `has_artifacts`，产物已删时自动隐藏失效的「产物」链接
- 安全：`_safe_dir()` 做 realpath 归属校验 + 字符白名单，**绝不触碰 `store/uploads/`**

**实测**：盘点正确识别孤儿；单删释放 4096B 并作废 1 个令牌、构建记录保留；
清孤儿移除 2 个目录释放 12288B；`_safe_dir` 对 `..`/`../../etc`/`uploads`/``/`a/b` 全部返回 `None`。

### 4.2 邮件改用 HTML 模板

**实现**：模板外置到 `app/templates/mail/`，共 5 个文件 ——
`layout.html`（统一外框）+ `build_ok.html` / `build_fail.html` / `verify.html` / `test.html`。

- `render_html(name, ctx, raw=())`：**默认对所有变量做 HTML 转义**，
  只有调用方在 `raw` 里显式列出的键才原样插入（用于已逐字段转义的整段 HTML）。

- `render_mail()`：正文片段 + 外框组合
- 模板名限定 `^[a-z0-9_]+\.html$`，**杜绝路径穿越**

  纯文本保留为 `multipart/alternative` 的降级分支

**实测**：`<script>` 与 `"` 属性注入均被转义；4 个模板结构完整（`<!DOCTYPE html>`…`</html>`，`<table>` 标签配平）；

### 4.3 文档一键安装部署

**新增 `install.sh`**（`sudo ./install.sh` 一条命令）：

```
识别发行版 → 装系统依赖（dnf/yum/apt，apt 走 --no-install-recommends）
→ 建 venv 装 Python 依赖（国内镜像优先，失败回落官方源）
```

关键设计：

- 支持 `--port` / `--host` / `--no-systemd` / `--dry-run` / `-y`
- **新增 `update.sh`**：`git pull` + 更新依赖 + 重启，明确不触碰运行时数据

**实测**：在 `python:3.11-slim` 容器里**真跑完整安装**（非仅语法检查），

## 五、需要我补充的信息

以下问题的答案**会改变审计结论**，请确认：

1. **部署形态：单进程还是多 worker？**（如 `uvicorn --workers 4` 或 gunicorn 多 worker）
   本项目有大量**进程内状态**：构建队列（`builder.QUEUE`）、登录失败计数、
   限速表（`_RATE`）、下载令牌密钥缓存、邮件线程池。多 worker 下这些**各自独立**，
   会导致：同一任务被多个 worker 抢、限速按 worker 数被放大 N 倍、
   排队位置不准。**当前实现只保证单进程正确。**
2. **是否部署在反向代理之后？** 若是，需确认代理是否重写了
   `X-Forwarded-Proto` / `X-Forwarded-Host`，以及是否**剥离了客户端伪造的这两个头**
   （应用侧已对 Host 做格式校验并优先取配置，但代理层剥离更彻底）。
3. **`ulimit -n` / systemd `LimitNOFILE` 的实际值？**
   本轮 fd 泄漏已修复，但构建与邮件链路本身也吃 fd；
   `install.sh` 生成的 unit **目前没有设置 `LimitNOFILE`**（继承 systemd 默认，
   部分发行版默认仅 1024）。是否需要我显式设成 65535？
4. **管理端「清空构建产物」是否需要二次确认或软删除？**
   当前是硬删（不可撤销）。若你希望保留「回收站」语义，需要改数据模型 —— 属产品决策。
5. **`/api/v1/build/{hash}` 仍是公开只读接口**，会返回签名下载链接（能力型 URL）。
   这是刻意设计还是应当加鉴权？**需确认**（上一轮已标记，至今未定）。
6. **第三方插件 feed**：119 个预置包中有 11 个第三方内核插件不在 OpenWrt 官方
   feed，勾选即构建失败（本地与 GitHub 后端都一样）。是否要接入第三方 feed？
   —— 这是产品能力边界，非代码缺陷，**需确认**。

   否则分代 GC 会把泄漏掩盖掉，这是本项最容易被写成假绿的地方。
2. **投毒索引（对应 F-4）**
   给一份 `Filename: ../../../../tmp/x.ipk` 的 Packages 索引，
   断言 `parse_index()` 后该条目的 `filename == ""`，且真实文件名（含 `~`）**不被误杀**
   （用真实索引的 1000+ 条做参数化回归）。
3. **数值配置边界（对应 F-2）**
   对每个 `t == "number"` 的配置项，用
   `["1e400", "-1e400", "nan", "inf", "", "abc", str(2**63)]` 参数化跑
   `validate()` 与 `_dec()`，断言**任何输入都不得抛出异常**。
4. **彩色/样式类配置的字符集（对应 F-3）**：`#";x"yy`、`#zzzzzz`、`#<svg>` 必须被拒。
5. **归档解压回归**：扩充 `tools/extract_regression.py`，加「索引文件名越界」与
   「gzip 炸弹」两组。
6. **邮件模板转义**：对每个模板注入 `<script>` 与 `"` 属性逃逸样本，
   断言输出中不含原始标签。
7. **安装脚本**：在 `debian:12` 与 `rockylinux:9` 容器里各跑一次
   `install.sh --no-systemd` → 启动 → `/healthz` 200 →
   `data/INITIAL_ADMIN.txt` 权限为 600 → 二次执行密码不变。
8. **多 worker 语义**（若最终要多 worker 部署）：起 4 个 worker，
   连打 20 次登录失败，断言**总**失败计数为 20 而不是分片计数。

## 七、不确定的地方（标注「需确认」，未编造）

1. **【需确认】多 worker 下的行为**：我在**单进程**下完成了全部实测。
   多 worker 部署会破坏进程内状态的一致性（见 §五.1），但我**没有在多 worker 下真跑过**，
   所以不给出具体量化结论 —— 需要你确认部署形态后，我再补这一项实测。
2. **【需确认】上游索引投毒的可行性边界**：F-4 我证明的是
   **「索引一旦被投毒即可任意文件写入」**，即污点可达性成立。
   至于上游 `dl.openwrt.ai` 与 ImageBuilder 自带 `repositories.conf` 被投毒的实际概率，
   取决于你的信任边界，**我不做判断**。
3. **【需确认】`store/uploads/` 的清理策略**：构建物已可逐个删除，
   但用户上传目录**只做只读展示、不提供删除入口**（避免误删用户文件）。
   是否需要单独的「清理孤儿上传」功能？属产品决策。
4. **【需确认】`install.sh` 生成 unit 未设 `LimitNOFILE`**：是否需要，
   取决于你机器上 systemd 的默认值（各发行版不同）。我未在目标机器上核实该默认值。
5. **【需确认】`prefetch` 的 `retention`/缓存失效**：`feeds_cache` 目前是
   24 小时 TTL 的 `Packages.gz` 缓存，**没有清理机制**。长期运行会缓慢增长
   （实测体量很小，未列为问题）。是否需要纳入清理？
