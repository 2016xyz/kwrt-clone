## 二、逐项实现

### 2.1 版本号：单一真源

新建仓库根 **`VERSION`** 文件为唯一真源（改这一个文件即发版）：

| 侧 | 读取方式 |
|---|---|
| Python | `app/version.py` → `VERSION = "1.0.1"` |
| PHP | `php/src/Version.php` → 读仓库根 `VERSION` 文件，失败才回落常量 |

显示位置：后台头部徽标、页脚、`/healthz`、`/api/v1/site`。

> 为什么不做成设置项：版本是**代码属性**，不是运营配置。放进后台会让人以为
> 改一下就能"升级"，而真正决定版本的是部署了哪份代码。

断言：`V-1`（文件与代码一致）、`V-4`（PHP 读到同一个值）。

### 2.2 安装即开机自启 / 更新即自动重启

**报错根因**：`update.sh` 在服务缺失时只打印「未检测到 systemd 服务 kwrt，请手动重启」。
而服务之所以缺失，通常只是当初用 `run.sh` 或 `install.sh --no-systemd` 装的
—— 这恰好是可自动修好的情况。

**做法**：把 systemd 逻辑抽成 `scripts/systemd-install.sh`，`install.sh` 与 `update.sh` 共用。
（原先两边各写一份，行为不一致 —— 这正是问题的来源。）

```
install.sh                 → 装 unit → enable（并验证）→ 启动
update.sh（服务已存在）     → --enable-only：只 enable + restart
update.sh（服务缺失）       → 自动装 unit + 开机自启 + 启动
退出码：0 成功 / 1 失败 / 2 环境不具备（无 systemctl 或未建 venv）
```

**同时修掉一个隐蔽的吞错**：

```bash
# 原实现 —— 失败了也不出声
run_root systemctl enable "$SERVICE_NAME" >/dev/null 2>&1 || true
# 现在 —— 报错并用独立命令复验
if run_root systemctl enable "$SERVICE_NAME" >/dev/null 2>&1; then …
else err "systemctl enable 失败 —— 开机不会自动启动"; exit 1; fi
if ! systemctl is-enabled --quiet "$SERVICE_NAME"; then err "enable 后仍不是 enabled"; exit 1; fi
```

**真跑验证**（独立服务名 `kwrt-sdtest`，测完已清理）：

| 路径 | 结果 |
|---|---|
| 新装 | `is-enabled=enabled`、`is-active=active`，unit 内容逐行核对通过 |
| `--enable-only`（update.sh 路径） | 跳过 unit 写入，enable + restart 成功 |
| 无 venv | 退出码 **2**（调用方据此降级，而非硬撑） |
| `--enable-only` 但服务不存在 | 退出码 **1** 并说明原因 |

### 2.3 登录/注册验证码（后台可自定义开关）

新增「安全与验证」分组，**全部默认关闭**（不替管理员决定）：

| 键 | 说明 |
|---|---|
| `security.captcha_enabled` | 登录验证码 |
| `security.captcha_on_register` | 注册验证码（**独立**开关） |
| `security.captcha_length` | 3–6 位 |
| `security.captcha_ttl_min` | 1–30 分钟 |

**六项安全性质，逐条实测**：

| # | 性质 | 实测 |
|---|---|---|
| 1 | 答案只存 sha256 哈希，库内无明文 | ✓（响应字段仅 `id/svg/ttl/length`） |
| 2 | 一次性：校验后立即作废 | ✓ 重放同 id 一律拒绝 |
| 3 | 有有效期 | ✓ 过期即拒 |
| 4 | 校验在**密码比对之前** | ✓ 否则撞库仍会消耗一次密码校验 |
| 5 | 按 IP 限流（60s / 30 张） | ✓ |
| 6 | 不依赖图形库（纯 SVG） | ✓ Pillow 装不上也不会让功能整块失效 |

**★ 一个必须记下的坑 —— 盐不能放在进程内**

初版用 `secrets.token_hex()` 做进程内盐。后果：`uvicorn --workers N` 时每个
worker 盐不同 → 用户在 A worker 取图、请求落到 B worker 校验 → **随机失败**，
且表现为「验证码明明输对了却说不对」，极难排查。

改为**持久化在 `app_secrets` 表**（安装级，全进程共享，随库备份迁移）。
`KWRT_CAPTCHA_SALT` 环境变量可显式覆盖（测试与多机共享用）。

**两版互通**（同一份 users.db 下的必要性质）：

```
PHP 签发 + Python 校验 → 200 ✓
Python 签发 + PHP 校验 → 200 ✓（小写答案亦通过）
```

靠三件事逐字节一致：同表 `captchas`、同盐 `captcha_salt`、
同哈希 `sha256("{salt}|{cid}|{CODE大写}")`。

### 2.4 多个 GitHub 构建队列

后台「GitHub 构建 → 构建队列（多队列）」填 JSON：

```json
[{"name":"主队列","repo":"owner/repo","token":"ghp_xxx",
  "workflow":"build-firmware.yml","ref":"main","enabled":true}]
```

| 性质 | 实测 |
|---|---|
| 多队列**轮转派发** | ✓ `A → B → A → B` |
| 队列参数**绑到实例**（不串号） | ✓ 每个实例读到的 repo/token/ref 互不干扰 |
| 缺 `repo`/`token` 的项**跳过** | ✓ 只活下合法项，不拖垮整体 |
| `gh.queues` 留空 → 回落单队列 | ✓ 老配置无需改动 |
| 禁用的队列被排除 | ✓ |

**为什么绑到实例上**：`dispatch()` 是**同步**的 —— 派发、轮询、取产物都在
同一次调用里完成，持有同一个 `self`。绑在实例上可保证整个生命周期用的是
同一个 repo/token，不会中途串到别的队列。

**PHP 侧**：`php/src/Queues.php` 同语义。顺带修正后台「测试连接」——
原先硬编码读 `gh.token`/`gh.repo`，多队列下**测 A 队列却派发到 B**，测试失去意义；
现在测的是轮转选中的、真正会被使用的那个队列。轮转游标存 `app_secrets` 表
（不能走 Settings —— 那套会按 schema 校验键名，而游标有意不进 schema）。

## 三、过程中被自己咬到的一次

`_serve_page` 里有个局部变量叫 `html`（页面正文），它**遮蔽了 `html` 模块**。
于是我新写的 `html.escape()` 抛 `'str' object has no attribute 'escape'`，
异常被 `except` 静默吞掉 —— 后台配的导航链接一条都不显示，日志里也只有一行警告。

**处置**：把局部变量改名为 `html_text`。教训是：在一个长函数里用与标准库同名的
局部变量，危险不在当下，而在**下一次有人往里加代码时**。

另一次：一个中途崩溃的测试脚本把 `gh.token` 写成了测试值、且没走到恢复分支，
导致后续 `git push` 鉴权失败。已恢复（API 校验 200）并推送成功。

## 五、仍未做 / 需确认

1. **【未做】PHP 侧的 GitHub 派发** —— PHP 仍是本地构建；`Queues.php` 只提供
   队列读取/选择（供后台测试连接与展示）。若要 PHP 也能派发远端构建，
   需要在 `php/src/Engine.php` 里实现 workflow_dispatch + 产物回传。
2. **【未做】多队列的按负载选择** —— 目前是简单轮转。若某队列更慢，
   轮转会把任务平均压给慢队列；按运行中任务数加权会更合理。
3. **【需确认】验证码难度** —— 当前是无第三方库的 SVG + 干扰线，
   能挡脚本但不挡打码平台。需要更强时建议接第三方验证码服务。
4. **【需确认】`VERSION` 是否有意纳入 CDN 缓存键** —— 目前静态资源版本号
   走 `site.asset_version`，与程序版本相互独立（改代码不必清 CDN）。若希望
   「程序版本一变就强制刷新 CDN」，需要把两者关联起来。
