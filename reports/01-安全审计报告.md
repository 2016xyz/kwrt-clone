## 二、致命与高危问题明细

> 所有"修复前"结论均附实测输出；未实测到的一律标注「需确认」。

### C-1 构建参数注入 → 远程命令执行（致命）

| 项目 | 内容 |
|---|---|
| **类型** | 注入 → 命令执行（CWE-78 / CWE-94） |
| **位置** | `app/builder.py:127`（`shell=True` ＋ f-string）；根因在 `main.py` 构建入口零校验 |
| **问题描述** | `ensure_imagebuilder()` 中有 `subprocess.run(f"zstd -dc {tarball} \| tar -xf - -C {tmp}", shell=True)`，而 `tarball` 由 `ib_dir_name(version, target)` 拼成，`target` **直接取自请求体且无任何白名单**。请求中的 `$( )` / 反引号 / `;` 会先经 make 变量展开、再经 shell 解析。 |
| **触发条件** | 匿名即可：自带 `Ng-One-Time-Verif-Value`（算法在前端 JS 里）＋ `POST /api/v1/build`，`target` 填注入串 |
| **实测证据** | ① 拼接结果确认 `;`、`#`、`$(` 未转义；② 隔离实验中 `make PROFILE='$(shell touch /tmp/XSP_MAKE_TEST)'` **成功创建文件**，证明到命令执行；③ ImageBuilder 已缓存（`cache/*.tar.zst` 81MB），说明链路真实可达 |
| **修复后代码** | 新增 `app/params.py` 字符白名单；`builder.py` 改为传参形态：<br>`script = 'zstd -dc "$1" \| tar -xf - -C "$2"'`<br>`subprocess.run(["sh","-c",script,"sh",tarball,tmp])` |
| **实测（修复后）** | `target="x86/64$(id)"` → `400 {"detail":"编译目标含有非法字符","error_code":"BAD_PARAM"}`；`profile="$(shell id)"` → 同样拒绝 |

**为什么这是最严重的一项**：`make VAR=value` 中 `$(shell ...)` 的展开是 make 的固有语义，**无法通过引号转义消除**——因此控制点必须在字符白名单（`params.py`），而不是命令拼接层。

### C-2 `/json/v1/{path}` 任意文件读取（致命）

| 项目 | 内容 |
|---|---|
| **类型** | 路径遍历 / 任意文件读取（CWE-22） |
| **位置** | `app/main.py:342`（原 `jsonapi`） |
| **问题描述** | `os.path.join(DATA,"json","v1",path)` 直接拼接路由路径。`os.path.join` **不处理 `..` 上跳**，Starlette 的 `{path:path}` 又原样透传未归一化路径 |
| **触发条件** | 匿名 GET |
| **实测证据（修复前）** | `GET /json/v1/../../../config.json` → **HTTP 200**，返回真实 `config.json` 内容；文件系统侧 `os.path.normpath("data/json/v1/../../../config.json")` = `config.json` 且 `isfile=True` 佐证 |
| **修复后代码** | 新增通用收口函数并应用于 `/json/v1`、`/langs/{name}`：<br>`full = safe_under(os.path.join(DATA,"json","v1"), path)` |
| **实测（修复后）** | 4 类穿越 payload（`../../../`、`%2e%2e`、`....//`、`../../../../`）**全部 404**，正常数据集 `overview.json` 仍 200 |

### C-3 下载令牌路径守卫被 `..` 绕过（高危）

| 项目 | 内容 |
|---|---|
| **类型** | 权限绕过 + 敏感文件泄露（CWE-22 / CWE-639） |
| **位置** | `app/dl.py:219`（`resolve_path`）、`app/main.py:2182`（利用入口） |
| **问题描述** | 守卫写作 `os.path.basename(request_hash) != "uploads"`，但 **`os.path.basename("..")` 返回的正是 `".."`**（非空、也不等于 `uploads`），遂通过校验，`STORE/..` 逃出存储目录 |
| **触发条件** | 需管理员会话（管理员调用 `reissue`），但这是守卫**本应独立拦截**的越权读 |
| **利用链** | ① `POST /api/v1/admin/tokens {action:reissue, request_hash:".."}` → 列出 `STORE` 上级（即项目根）文件并为每个文件签发令牌（含 `users.db`）→ ② 持令牌访问 `/dl/t/<token>` → ③ 下载 `users.db` |
| **后果放大** | `users.db` 内含 `users.password`（口令哈希）与 `dl.secret`（**下载令牌 HMAC 签名密钥**）——等价于同时拿到全部离线爆破素材与令牌伪造能力 |
| **实测证据（修复前）** | `dl.resolve_path("..","users.db")` → `store/../users.db`，`isfile=True`；`settings` 表中确认存在 `dl.secret` |
| **修复后代码** | 任务 ID 白名单 ＋ realpath 归属校验：<br>`if not HASH_RE.match(h) or h == "uploads": return None`<br>`if p != base and not p.startswith(base + os.sep): return None` |
| **实测（修复后）** | `resolve_path("..","users.db")` → `None`；`reissue("..")` → `400 任务 ID 非法`；`/store/../users.db`、`/store/../config.json`、`/store/../app/pay.py` → 全 404 |

**同类点位一并收敛**：`main.py` 另有 4 处 `os.path.basename(request_hash)` 拼路径（构建删除、`/store/{hash}/`、`/store/{hash}/{name}`），同根因，已统一改用 `check_hash_id()`。

### H-2 支付宝响应未验签即判成功（高危）

| 项目 | 内容 |
|---|---|
| **类型** | 认证/加密实现缺陷（CWE-347） |
| **位置** | `app/pay.py` `call()` |
| **问题描述** | 仅凭 `code == "10000"` 判成功，**不看 `verified`**。而 `verified` 正是响应体 RSA 验签结果——等于信任未验签报文，中间人可伪造成功响应 |
| **修复后代码** | `ok = (code == "10000") and verified`，且 `code==10000 但未验签` 时明确报错拒绝 |
| **备注** | 顺带把 `verify()` 的异常捕获从 `except (..., Exception)` 收窄为 `(InvalidSignature, ValueError, TypeError)` ＋ 记日志，避免把编程错误伪装成"验签失败" |

### H-3 资金类并发重复发放（高危）

| 子项 | 位置 | 问题 | 修复 |
|---|---|---|---|
| 订单结算 | `main.py:1115` `_settle()` | 分支只判断 `status=="paid"`，**不含 `paid_pending`**；支付宝异步通知与前端查单会并发触发（TOCTOU），同一笔订单可重复顺延赞助天数 | 改为条件更新原子抢占：`UPDATE ... WHERE status NOT IN ('paid','paid_pending','refunded')`，以 `rowcount` 判定 |
| 人工确认 | `main.py` `admin_pay_order` | 允许对 `paid` 状态再次 `confirm`，管理员点两次发两次权益 | 仅 `paid_pending` 可发放，且用条件更新保证只生效一次（冲突返回 409） |
| 退款审核 | `refund.py:approve()` | 「先读 `pending` → 调网关 → 再写状态」三步非原子，两次点击/并发会**调用真实退款网关两次**，造成真实资金损失 | 引入 `processing` 中间态 + 原子抢占；网关失败/参数缺失均回滚为 `pending` |

### H-4 口令与认证（高危）

| 子项 | 问题 | 修复 |
|---|---|---|
| 口令存储 | 无盐 SHA256，可彩虹表/GPU 爆破 | PBKDF2-HMAC-SHA256（240,000 次迭代 + 16 字节盐），历史无盐哈希在登录成功后**自动升级** |
| 登录爆破 | 无任何限速，实测连打 12 次全部 `403`，可无限尝试 | 账号 + IP 双维度失败计数，8 次锁 5 分钟（实测第 9 次起 `429`） |
| 会话固定 | 登录前后会话令牌不变 | 登录成功作废旧令牌、换发新令牌（`token_hex(32)`） |
| 默认口令 | 模块导入即 `INSERT OR IGNORE admin/admin123`，**每个部署都带已知口令** | 仅当库中无任何管理员时创建；口令取自 `KWRT_ADMIN_PASSWORD` 或随机生成并打印 |
| 用户名抢占 | 可注册 `admin` 等保留名 | 新增 `RESERVED_NAMES` 拒绝 |

### H-5 CSRF（高危）

| 项目 | 内容 |
|---|---|
| **问题描述** | 全部写接口依赖 cookie 会话（`samesite=lax` 对表单 POST 不设防），且接口同时接受表单编码，**无任何 CSRF 防护** |
| **修复** | 全局中间件：非安全方法校验 `Origin`/`Referer` 与请求 Host 同源；`/api/v1/alipay/*` 豁免（外站发起，靠验签保护） |
| **实测（修复后）** | ① curl 带跨站 Origin → `403`；② **真实浏览器**：在 9999 端口起攻击者页面，自动提交跨站表单到 8443（会话 cookie 已随请求发出）→ 公告值**未被修改**，防护生效 |
