## 1. F1 · `/firmware` 反射型 XSS（高）

### 位置

`app/main.py::firmware_list`（`GET /firmware/{target:path}`）

### 根因

`target`（路径段）与 `dev`（查询参数）直接取自 URL，被 f-string 拼进 `HTMLResponse`，**没有任何转义**：

```python
# 修复前
if not rows:
    return HTMLResponse(
        f"<h3>暂无 {target}{('/' + dev) if dev else ''} 的构建产物</h3>"
        f"<p>请在首页选择设备并构建。</p>")
...
li = "".join(f'<li><a href="{u}">{n}</a> ...' for u, n, s, mt, _h in rows)   # u / n 同样未转义
return HTMLResponse(
    f"<h3>{target}{('/' + dev) if dev else ''} 固件列表</h3>"
    f"<p>共 {len(rows)} 个文件</p><ul>{li}</ul>")
```

`u = f"/store/{h}/{n}"`、`n` 是产物**文件名**，也一并未转义。

### 为什么「会执行」而不是「只是脏 HTML」

`app/netcfg.py::security_headers()` 的 CSP：

```
Content-Security-Policy: default-src 'self'; img-src 'self' data: blob:;
  style-src 'self' 'unsafe-inline';
  script-src 'self' 'unsafe-inline' 'unsafe-eval';   ← 允许内联脚本
  connect-src 'self'; frame-ancestors 'self'; base-uri 'self'; form-action 'self'
```

`script-src` 带 `'unsafe-inline'`，注入的 `<script>` **确实会执行**。

### 实证（修复前，线上 origin）

```http

Host: op.2016xlx.cn

HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8

<h3>暂无 <script>alert(document.domain)</script> 的构建产物</h3><p>请在首页选择设备并构建。</p>
```

另两个向量（均 200 且原样回显）：

```
GET /firmware/x86/64%3Cimg%20src=x%20onerror=alert(1)%3E    → <h3>暂无 x86/64<img src=x onerror=alert(1)> 的构建产物</h3>
GET /firmware/x%3Csvg%20onload=alert(1)%3E                    → <h3>暂无 x86<svg onload=alert(1)> 的构建产物</h3>
GET /firmware/x?dev=%3Cb%3Epwn%3C/b%3E                        → <h3>暂无 x/<b>pwn</b> 的构建产物</h3>
```

### 为什么是「双端不同步」而非孤立疏漏

PHP 侧同一路由是转义的 —— `php/templates/firmware.php`：

```php
<h1><?= e($target) ?> / <?= e($id) ?></h1>
<a class="btn btn-primary" href="/?target=<?= e(urlencode($target)) ?>&id=<?= e(urlencode($id)) ?>">去定制</a>
```

### 修复

```python

#   n/u 是产物文件名与链接 —— 直接拼进 HTML 就是反射型 XSS。
label = html.escape(target + (("/" + dev) if dev else ""))

li = "".join(
    f'<li><a href="{html.escape(u, quote=True)}">{html.escape(n)}</a> '
    f'<small>{s / 1048576:.1f} MB · '
    f'{time.strftime("%Y-%m-%d %H:%M", time.localtime(mt))}</small></li>'
    for u, n, s, mt, _h in rows)
```

## 2. F2 · PHP 后端解压用户包零校验 + 格式错配（中）

### 位置

`php/src/Engine.php::injectDefaults()`（修复前 L290-296）

```php
// 修复前
$fp = (string) ($this->payload['files_path'] ?? '');
if ($fp !== '') {
    $src  = Config::path('store', 'uploads', ltrim($fp, '/'));
    $real = Util::under(Config::path('store', 'uploads'), $src);
    if ($real !== null && is_file($real)) {
        $this->runCmd(['tar', '-xzf', $real, '-C', $ib . '/files'], $ib);
    }
}
```

三个问题叠在一起：

1. **零条目校验** —— Python 侧有 `builder._safe_extract()`（逐条查 `../`、绝对路径、符号链接、设备文件），PHP 侧**从来没有**过对应实现。文件里甚至没有任何一处校验代码。
2. **格式错配** —— `tar -xzf` 只认 gzip；而上传白名单（`ApiController` L647、前端 `accept`、错误文案）都写着 `.zip / .7z / .tar.gz / .tgz`。后三种之外的两个格式在 PHP 后端**必然解压失败**。
3. **失败被吞** —— `runCmd` 的返回值没接，失败等于成功。

### 实证：越界到底能不能成功？（这条我做了两次，第一次的结论是错的）

第一个复现脚本我自己写坏了 —— 造包时用 `echo > $S/link/pwned.txt` 顺着符号链接就把文件写进了 `outside`，造成「越界成功」的**假阳性**。清理后重做，用纯 Python 只往包里写、绝不触碰真实文件系统：

```
$ python3 -c "...TarInfo('link') SYMTYPE -> <outside>; TarInfo('link/pwned.txt')..."   # 只构造包
$ tar -tzf a.tar.gz
    link
    link/pwned.txt
$ mkdir -p ib/files outside     # outside 初始为空
$ tar -xzf a.tar.gz -C ib/files
    tar: link/pwned.txt: Cannot open: Not a directory
    tar: Exiting with failure status due to previous errors
    退出码: 2
    outside 内容: (空)          ← 未越界
```

三条向量都试了：

| 向量 | GNU tar 1.34 的行为 | 越界写入 |
|---|---|---|
| 条目名含 `../` | `tar: Removing leading '../'` + `Member name contains '..'` → 拒绝，退出码 2 | **否** |
| 条目名为绝对路径 | `tar: Removing leading '/'` → 改写成相对路径，落在 `files/` 内 | **否** |
| 符号链接成员 + 借链接写出的后续条目 | `Cannot open: Not a directory` → 阻断 | **否** |
| 硬链接指向 `/etc/passwd` | `Removing leading '/'` → `No such file or directory` | **否** |

### 结论（据实修正定级）

**在这台机器上（GNU tar 1.34）不可越界写出。** tar 自己就把这三类条目挡住了。

但这不等于原代码没问题，三点仍然成立且必须修：

1. **安全防线完全不在代码里**。能否挡住，取决于构建机上 `tar` 的实现与版本 —— busybox tar、老版本 GNU tar、（`--absolute-names` 等开关一旦被加上）都不具备这层保护。同一产品在另一台机器上部署，结论可能完全不同。**安全不能靠外部工具的默认行为兜底。**
2. **`.zip` / `.7z` 在 PHP 后端 100% 失败** —— 用户上传这类包，构建"成功"但文件全丢。
3. **失败被静默忽略** —— 不退码、不提醒。

### 修复

新增 `php/src/Archive.php`（`Kwrt\Archive::safeExtract`），与 Python `_safe_extract` 判据对齐：

- `.zip` → 复用 `Github::safeUnzip`（已有实现，逐条校验 + 丢弃越界条目）
- `.tar.gz` / `.tgz` / `.tar` → 先 `tar -tzf` 列成员名校验（绝对路径 / `..` / NUL），再 `tar -tzvf` 查类型（`l` 符号链接 / `h` 硬链接 / `b` `c` 设备 / `p` `s`），全部通过才解压
- `.7z` → 先 `7z l -slt` 列清单校验（含链接目标是否落在 dest 内），再 `7z x`

`Engine.php` 改为调用它，并让失败**变成构建失败**：

```php
try {
    Archive::safeExtract($real, $filesDir);
} catch (\Throwable $e) {
    throw new \RuntimeException('自定义文件包解压失败：' . $e->getMessage());
}
```

并且**先列校验、后解压**（绝不"先解压再检查"——那时文件已经落盘了）。

### 实证（修复后）

同一个包走新代码：

`php/scripts/archive_selftest.php` —— **20/20 全部通过**：

## 3. F3 + F4 · 7z 链路与 files_path 的静默失效（中）

### 根因

```python
# app/builder.py（修复前）
if lower.endswith(".7z"):
    # 没有 stdlib 支持，只能交给系统工具；解压后校验（7z 未安装时会失败）
    tool = ["7z", "x", "-y", f"-o{dest}", archive]
    try:
        subprocess.run(tool, check=True, capture_output=True, timeout=300)
    except Exception as e:
        raise RuntimeError(f"解压 {os.path.basename(archive)} 失败: {e}")
    for root, _dirs, names in os.walk(dest):              # ← 空转校验
        for n in names:
            if not _inside(dest, os.path.join(root, n)):
                raise RuntimeError(f"归档包含越界路径: {n}")
```

两个独立缺陷：

1. **「解压后再校验」是空转的**。越界条目已经写到 `dest` 之外，而校验只 `os.walk(dest)` —— 越界的东西永远不在 `dest` 里，因此这条 `raise` **不可能被触发**。它给人"有校验"的错觉，实际拦截数为 0。
2. **本机根本没装 7z**（`install.sh` / `run.sh` 的依赖清单是 `unzip tar`，没有 p7zip）。所以 `.7z` 分支必然抛错。

而调用方把异常吞了：

```python
# app/builder.py（修复前）
if src:
    try:
        _safe_extract(src, files_dir)
    except Exception as e:
        print("[builder] extract files_path failed:", e, flush=True)   # ← 只打印，继续构建
```

**用户视角**：上传 `custom.7z` → 上传接口收下（白名单里有 `.7z`）→ 提交构建 → 构建"完成" → 下载固件，**自定义文件一个都不在**。全过程零报错。

`files_path` 指向的文件被清理掉时同理（`src` 为空、`if src:` 不进、静默继续）。

### 实证（线上）

修复前 `which 7z`：

```

（无输出）

bash: 7z: command not found
```

修复后上传即拒：

```http

Content-Type: multipart/form-data; boundary=----kwrt7

7z¼¯'...
```

### 修复

- `builder.sevenzip_exe()` / `sevenzip_available()`：探测 `7z`/`7za`/`7zr`
- 7z 分支改为**先 `7z l -slt` 列清单校验、再解压**（空转校验删除）
- 未装 7z 时 `_safe_extract` 抛「服务器未安装 7z…（请改用 .zip / .tar.gz）」人话
- 上传接口遇到 `.7z` 且无 7z → **400 提前拒绝**
- 解压失败 / `files_path` 未命中 → **构建失败并把原因回给用户**，不再静默：

```python

        "detail": f"自定义文件包解压失败：{e}", ...}
...

        "detail": f"自定义文件包不存在或已被清理（{fp}），请重新上传后再构建", ...}
```

## 4. F5 · `_entry_block()` App 分支未转义（中）

### 位置

`app/main.py::_entry_block()`（注入到**每一个公开页**的 App 下载 / 公众号弹层）

### 根因

同一个函数里两套写法 —— 公众号分支全部 `html.escape`，App 分支一个都没有：

```python
# 修复前 —— App 分支
name = str(SS.get("entry.app_name") or "Kwrt 助手")
...
links += f'<a class="btn btn-primary" href="{apk}" rel="noopener">Android 下载 APK</a> '
qrimg = (f'<img src="{qr}" alt="App 下载二维码">' if qr
         else f"<div class='qr' data-qr='{apk or ios}'></div>")     # ← 单引号属性，值里含 ' 直接逃逸
out += (... f"<h3>{name}</h3><p ...>{desc}</p>" ...)

# 修复前 —— 公众号分支（同一函数）
out += (... f"<h3>{html.escape(nm)}</h3>"
        f"<p ...>{html.escape(hint)}</p>" ...)
```

## 5. F6 / F7 / F8 · 低危项

### F6 · `set_setting()` 的兜底分支绕过 schema 校验

```python
# app/main.py（修复前）
def set_setting(key, value):
    """统一配置写入入口 —— 经 schema 校验后落库。"""      # ← 文档承诺
    try:
        return SS.set_(key, value)                        # 走 validate()
    except Exception:
        with db() as c:                                   # ← 异常时把**原始值**直写库
            c.execute("INSERT OR REPLACE INTO settings(key,value,updated) VALUES(?,?,?)",
                      (key, str(value), time.time()))
```

任何被 `validate()` 拒绝的值（超范围数字、非法颜色、超长文本……）都能经由这条路落盘，之后再被 `public_values()` 或页面渲染取出来用。**这就是 F5 那类注入的放大器**。

修复：schema 里**已知**的键校验失败必须抛出，只有 schema 之外的历史键才走兜底。

### F7 · 死参数与 hostname 双端不同步

```python
# app/params.py（修复前）

```

## 6. F9 · 我自己修出来的 bug（诚实记录）

修 F2 时我写了这段：

```php
$flags = str_ends_with($lower, '.tar') ? '-tf' : '-tzf';
foreach (self::lines([$tar, str_replace('-tf', '-tvf', $flags), $archive]) ...) {   // ← 错
```

`'-tzf'` 里**并不含**子串 `'-tf'`（是 `- t z f`），所以 `str_replace` 静默不生效 —— 命令还是 `tar -tzf`，拿**名字列表**当**类型列表**用，`$line[0]` 恒是普通字符，符号链接检查永远不命中。

新写的 `archive_selftest.php` 当场抓出来（那一条红）：

```
  ✗ 含符号链接成员 → 拒绝  没有抛错！
```

改成显式给出 `-tf/-tvf/-xf` 与 `-tzf/-tzvf/-xzf` 后：

```
  ✓ 含符号链接成员 → 拒绝  lrwxrwxrwx root/root 0 2026-10-04 20:20 esclink -> /etc
合计 20 项，全部通过 ✓
```

**这就是"先列校验、后解压"的价值 —— 但前提是类型检查真的执行了。** 一个不生效的校验比没有校验更危险：它让人以为已经挡住了。

## 7. 攻击链与下一步

### 已确认可组合的链

`F6`（`set_setting` 校验后门）会放大任何"能写 settings 但被 validate 拒绝"的路径 —— 例如把超长/非法值落库后再由页面渲染取出。

5. **构建机 tar 版本纳入部署前置检查**：既然穿越防护已进代码，这一条只是可观测性补充。

## 9. 一句话总结

**这一轮真正危险的是 F1**（一条 URL 就能在用户浏览器里执行脚本，而 CSP 还特意为 Vue 留了 `unsafe-inline`）；**最该记住的是 F3**（不是漏洞，是"看起来成功了其实什么都没做"——这类静默失效比报错更难发现）；**最该警惕的是 F9**（我自己的修复里也藏了一个不生效的校验，靠新写的自测才暴露——**没有测试的"安全修复"和没有修复差别不大**）。
