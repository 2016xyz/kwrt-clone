## 二、核心缺陷：界面构建 100% 失败

### 现象

界面的「固件分支」下拉框给的是**分支号**：

```html
<option value="25.12">25.12 (25.12.5)</option>
```

而下载 ImageBuilder 需要的是**发布号**，镜像站只认后者：

```
https://downloads.openwrt.org/releases/25.12/targets/x86/64/      → 404
https://downloads.openwrt.org/releases/25.12.5/targets/x86/64/    → 200
```

PHP 侧提交构建时**不做任何解析**，直接把 `"25.12"` 存进 payload 并拿去拼下载地址。

### 实测复现（用界面的真实取值提交）

```
POST /api/v1/build   {"version":"25.12", ...}
→ {"status":"ok","request_hash":"ef03b3...","detail":"已开始构建"}   ← 看起来正常

25 秒后：job: failed  "RuntimeException: 无法下载 ImageBuilder（已尝试多个镜像）"
```

用户看到的是「已开始构建」然后永远失败，**没有任何可自解的线索**。

### ★ 为什么此前一直没发现 —— 本轮最值得记下的教训

真编测试脚本自己传的是**发布号**：

```python
TARGET, PROFILE, VERSION = "x86/64", "generic", "25.12.5"   # ← 测试作者的理解
```

而界面提交的是**分支号**。**测试取值与真实路径取值不一致 —— 测了等于没测。**
端到端用例全绿，真实用户 100% 失败。这类漏洞靠审代码也很难发现，
因为两侧代码单看都是「对的」。

**现在用例会自己断言**：

```
界面版本下拉框取值: 25.12  → 提交值 '25.12' 必须与之相同  [一致 ✓]
```

对不上直接报错 —— 防止将来界面改了而用例悄悄失去覆盖。

### 修复

新增 `php/src/Releases.php`，与 Python `app/releases.py` 的 `resolve()` **逐条同源**：

| 提交值 | 解析结果 | 包管理器 |
|---|---|---|
| `25.12` / `25.12.5` | `25.12.5` | apk |
| `24.10` / `24.10.8` | `24.10.8` | opkg |
| `23.05` / `23.05.6` | `23.05.6` | opkg |
| 其他 / 空 | 默认最新分支 | — |

刻意保留 Python 侧两条**曾经是真实缺陷**的边界行为：

- 只接受 `major.<1–3 位数字>`，所以 `25.120` **不会**被误判进 25.12 分支；
- 请求 `25.12.9` **不会**被静默换成 `25.12.5` ——
  否则用户以为按指定版本构建、实际不是。

响应里回带 `version`，让用户看得见实际构建的是哪个版本。

### 验证（真编，用界面真实取值）

```
界面版本下拉框取值: 25.12  → 提交值 '25.12'  [一致 ✓]
提交构建: 200  {"request_hash":"c4820d6e...","version":"25.12.5"}   ← 已正确解析
[ 777.5s] done — 构建完成，共 12 个文件
可启动镜像: 7 个 ✓
下载链接: 3/3  sha256 一致=True         ← 修复前是 0/3（全部 403）
```

## 四、顺带修：失败时 `builds.status` 不同步

`Builder::fail()` 只写 `jobs.status='failed'`，`builds.status` 仍停在 `'queued'`。

状态接口优先读 `jobs`，所以**界面显示是对的**；但后台列表、「我的订单」等
直接查 `builds` 的地方会一直显示 `queued`，像是永远没开始。
两处状态不一致本身就是 bug，排查时极易误导。现已同步回写。

## 五、一个排查过程记录：响应式用例超时 ≠ 页面坏了

`responsive_check.py` 一度在 `networkidle` / `domcontentloaded` 上超时，
看着像是我改坏了页面渲染。逐步排查：

| 检查 | 结果 |
|---|---|
| `curl` 各页面与静态资源 | 全部 **200**，耗时 **12–30 ms** |
| 5 个请求并发（线程池） | 总计 **0.08 s** |
| 同一条连接复用发 5 个请求 | 总计 **0.144 s** |
| 浏览器内实际状态 | Vue/jQuery 已加载、站点数据已渲染、3 个 fetch 均 **<0.3 s**、图片 `onload` |

**页面完全正常**。真实原因：

```
Swap: 2047 total, 2047 used      ← 交换区 100% 占满
Mem:  6604 total, 4995 used, available 1606
```

机器上两个 `pyright-langserver`（947 MB + 716 MB）加上 web-ui（903 MB）
把内存压满，Chromium 被换出到已满的 swap 上，表现为计时剧烈抖动
（同一次导航 14.8 s → 5.4 s → 0.7 s）。释放后 **104/104 全部通过**。

> **教训**：浏览器用例超时时，先用 `curl`/并发/连接复用把「服务端慢」证伪，
> 再查系统资源。否则容易去改本来没坏的代码。

另外记录一个**误导性线索**：我早期用 Playwright 的 `request`/`response`
事件日志判断「3 个请求未完成」，但页面内实测这些请求**都完成了** ——
事件日志在页面加载竞态下会漏报，不能单独作为「请求失败」的证据。

## 六之二、同轮的又一处「两版不一致」：PWA / SEO 只在 PHP 侧实现

收尾复验时发现 `/manifest.webmanifest` 与 `/service-worker.js` 在 Python 侧返回 404。
第一反应是「回归」，查下来是**功能缺口** —— 这两个路由 Python 从未实现过。

性质与「域名/CDN/页面开关」完全相同：设置项 `entry.pwa_enabled` 加在两版共用的
schema 里、**默认还是开启的**，但只有 PHP 版实现了。于是 Python 后台能改这个开关、
前台毫无反应 —— 又一处「假功能」。

### 补齐的路由（与 PHP 同源）

| 路由 | 说明 |
|---|---|
| `/manifest.webmanifest` | Web App Manifest（名称/图标/主题色取后台设置） |
| `/service-worker.js` | 离线兜底 + 静态资源缓存 |
| `/offline.html` | 断网回落页（纯静态，不依赖外部资源） |
| `/robots.txt` | **自动 Disallow 已被后台关掉的页面** |
| `/sitemap.xml` | 只收录仍开启的公开页面 |

Service Worker 里写死两条纪律，都是踩过的坑：

- **`/api/` 一律走网络、绝不缓存** —— 否则用户会拿到过期的构建状态；
- **SW 自身绝不长缓存**（`no-cache, must-revalidate`）—— 否则新版永远发不出去。

页面里自动注入 `<link rel="manifest">`、`<meta name="theme-color">` 与 SW 注册脚本。
缺这几行，「添加到主屏幕」拿不到图标与名称、断网也没有兜底页 —— **装了等于白装**。

### 一个静默的坑：图标 MIME

图标类型原先直接写死 `image/png`，而实际 logo 是 `.svg`。
给 `.svg` 声明 `image/png`，浏览器会**静默拒绝**该图标（PWA 装上后是白块），
**不报任何错、控制台也没有提示**。已改为按扩展名推导。

### 验证

| 项 | 结果 |
|---|---|
| P-4b（新增） | 五个路由齐备 + MIME 正确 + **图标类型与扩展名匹配** + robots 含 `/admin/` + sitemap 合法 |
| P-4c（新增） | 页面确实注入了 manifest 链接与 SW 注册（防「路由存在但页面不引用」） |
| `verify_python_features.py` | **9/9** |
| 站点 14 个路由 | 全部 200 |
| 其余回归 | PHP 26/26、round5 13/13、extract 12/12、u_fixes 10/10、响应式 **104/104** |

### 由此沉淀出一条机械检查（已落地）

既然两版共用同一份设置 schema，那么**任何只在一侧实现的开关都是缺陷**。
据此写了 `tools/verify_switch_parity.py`，三层：

| 项 | 内容 |
|---|---|
| S-1 | **Python**：逐开关翻转，断言「开→200 / 关→404 / 可恢复」 |
| S-2 | **PHP**：同样逐开关翻转（起独立实例 + 独立测试库） |
| S-3 | 兜底 tripwire：schema 里 14 个 `*_enabled` 键必须在两版源码中**都被引用** |

**这条检查立刻又抓到一个真缺陷**：`entry.pwa_enabled` 在 Python 侧有 gate、
**PHP 侧没有** —— PHP 的 `/manifest.webmanifest` 与 `/service-worker.js` 不受开关管辖，
后台关掉 PWA 在 PHP 侧毫无效果。已修。

两个实现细节值得记下：

- **PHP 侧不要用 `php -r` 传带命名空间的调用** —— 多层反斜杠转义极易写错，且失败是
  **静默的**，会让人误判成「这个开关压根没实现」。改用独立脚本
  `php/scripts/set_setting.php`，失败即非零退出。
- **`/offline.html` 刻意不受 PWA 开关管辖**（它是 SW 的兜底页，两版一致地始终提供）。
  把它写进「关了应 404」的列表会得出错误结论 —— 检查本身也要选对断言对象。
