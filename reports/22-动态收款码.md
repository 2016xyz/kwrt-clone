# 22 — 收款码图片地址：用户输入金额点击后动态生成

- **版本**：v1.0.5 → **v1.0.6**
- **需求**：赞助页让用户**输入金额**，点击后**动态生成收款码图片地址**
- **状态**：已实现（Python + PHP 双端）、已部署、已用真实浏览器与真实解码器验证

## 1. 需求落点

用户原话：**「收款码图片地址在用户输入金额点击后动态生成」**。

拆开是两件事，之前**两件都没有**：

1. 赞助页没有「输入金额」的地方 —— 只能从后台配死的套餐里选。
2. 「收款码图片地址」（后台 `sponsor.pay_qr`）是个**静态图片 URL**，而且
   在 Vue 前台**从来没被渲染过**（只挂在 PHP 的 `fadian.php` 上），
   属于"后台能配、前台看不见"的静默失效。

按确认的方案实现为**双通道**：

| 通道 | 触发条件 | 返回的「收款码图片地址」 |
|---|---|---|
| `alipay` | 站点开通了支付宝当面付且密钥齐全 | 该笔订单的二维码 `/api/v1/sponsor/pay/{订单}/qr.png`，金额由支付宝带货，轮询自动到账 |
| `manual` | 没开当面付 | **服务端按金额实时生成**的 `/api/v1/sponsor/qr.png?amount=…` |

> ⚠️ **更正前一轮的结论**：我先前说"线上没配支付宝当面付"是**读错了设置键名**
> （查了不存在的 `pay.enabled`，真键是 `pay.alipay_enabled`）。
> 实测 `pay.available() = true`、`sign_verified = true` ——
> **线上支付宝当面付一直是可用的**，只是缺"自定义金额"这个入口。

## 2. 新增后台设置（`sponsor` 分组）

| 键 | 类型 | 默认 | 作用 |
|---|---|---|---|
| `sponsor.qr_kind` | select | `image` | `image` = 用固定图片；`text` = 用下面的内容实时生成 |
| `sponsor.qr_text` | textarea | 空 | 收款码**内容/链接**，支持 `{amount}` / `{amount2}` 占位符 |
| `sponsor.custom_amount` | bool | `true` | 是否允许用户自定义金额 |
| `sponsor.min_amount` | number | 1 | 金额下限 |
| `sponsor.max_amount` | number | 99999 | 金额上限 |
| `sponsor.per_day_price` | number | 0 | 自定义金额的每天单价；0 = 取套餐里最划算的那个 |
| `sponsor.custom_amount_auto` | bool | **false** | 自定义金额是否也允许自助确认（见 §5） |
| `sponsor.pay_qr` | text | 空 | 原有字段，改为「`image` 模式下用的固定图片地址」 |

`{amount}` 会被替换成 `50` / `4.99` 这种紧凑写法，`{amount2}` 固定两位小数。
例：`https://qr.alipay.com/fkxXXXX?amount={amount}` → 用户输入 50 时生成
`https://qr.alipay.com/fkxXXXX?amount=50` 的二维码。

### 跨字段校验（新增 `cross_check` / `crossCheck`）

单字段校验看不到"两个值之间"的关系，批量保存才会暴露：

- `min_amount > max_amount` → **两个键一起拒绝写入**（保留旧值），
  只落一半的区间比不落更危险；
- `qr_kind=text` 但 `qr_text` 为空 → 警告（照常保存）："用户点击生成收款码时会失败"；
- `qr_kind=text` 但内容里没有 `{amount}` → 警告："生成的收款码不会带上用户输入的金额"。

> 两版都必须用 `elif` 串起来 —— 第一版写成两个独立 `if`，
> 于是"内容为空"被后面那条"缺 `{amount}`"**覆盖**掉，提示指错了要改的地方。

## 4. PHP 端：零依赖二维码生成器 `php/src/Qr.php`

PHP 版**没有**任何二维码能力（原来的 `sponsorPayQr` 是 `302` 跳到支付宝返回的
`qr_code` 链接 —— 对"当面付"有效，对站长自己的收款码无效，没有可跳的目的地）。
也不能引第三方：收款内容里含站长的收款标识，交给外部二维码接口等于把收款信息送人。

于是按 Python 版同一原则，用**标准库**实现了字节模式/纠错等级 M/版本 1–20 的
QR 编码器（Reed–Solomon 纠错、8 种掩码罚分择优、格式/版本信息 BCH），
再用 `gzcompress` + 手写 PNG chunk 输出 1 bit 调色板图。

**正确性不是"看着像"就收工** —— 与参考实现 `python-qrcode` 做了逐格比对：

```
掩码逐格比对：48/48 一致        （6 个用例 × 8 个强制掩码）
自动选掩码：6/6 落在 8 个合法掩码结果内
用例0:  40 字节 → 矩阵  29x29
用例1:  51 字节 → 矩阵  33x33
用例2:  80 字节 → 矩阵  37x37
用例3: 200 字节 → 矩阵  57x57    ← 起进入版本信息区（≥7）
用例4: 400 字节 → 矩阵  77x77
用例5: 600 字节 → 矩阵  93x93
```

逐格比对只能证明"码图对"，**证明不了"能扫出来"**。所以又用真实解码器
（OpenCV `QRCodeDetector`）解服务器产出的 PNG：

```
用例0 (40字节, 363px)  → 解码一致 ✓
用例1 (51字节, 333px)  → 解码一致 ✓
用例2 (80字节, 328px)  → 解码一致 ✓
用例3 (200字节, 366px) → 解码一致 ✓
用例4 (400字节, 486px) → 解码一致 ✓
用例5 (600字节, 582px) → 解码一致 ✓
PNG 实解：6/6
```

这一步抓出了两个**逐格比对永远抓不到**的缺陷（见 §6）。

## 5. 安全设计

| 点 | 做法 | 理由 |
|---|---|---|
| **天数永远服务端算** | 套餐走套餐的 `days`；自定义金额走 `_custom_days()` / `customDays()` | 前端传来的只有 `amount`（用户的申报值，本来就要）。若天数也能由前端指定，就是「付 1 元给 3650 天」。原实现注释写着"绝不采信前端的 amount/days"，自定义金额放开了 amount 那一半，days 这半必须守住 |
| **天数上限 3650 天** | `max(1, min(days, 3650))` | 否则一个很大的金额配很小的单价会算出几十年，把 `sponsor_until` 推成"永久" |
| **自定义金额默认不自助确认** | 新增 `sponsor.custom_amount_auto`，默认 **false** | 套餐金额是站长定的，自助确认风险有界；自定义金额是**用户自己填**的，一旦允许自助确认就等于让用户凭空给自己发任意时长。默认落 `pending`，由后台「赞助申请」人工确认 |
| **`qr_text` 不下发前台** | 只下发 `qr_kind` / `custom_amount` / 区间 / 单价 | 收款内容本身是半敏感，前台只需要知道"能不能自定义金额、区间多少" |
| **金额走白名单式替换** | 替换进模板的金额是服务端 `float()` + `round(2)` 后的数字 | 占位符之外的内容原样保留，金额这个入口无法注入别的字符 |
| **金额必须过范围校验** | `1 ≤ amount ≤ max_amount`，非数字给人话 | 用户输入会进图片内容，必须先做数值校验 |
| **二维码必须本地生成** | `Qr.php` / `pay.qr_png_bytes` | 收款信息不出站 |

## 6. 顺带修掉的 5 个问题

1. **PHP `Pay::grant()` 覆盖 `sponsor_amount`**（应为**累加**）。
   Python 写的是 `sponsor_amount = COALESCE(sponsor_amount,0)+?`；PHP 是直接覆盖 ——
   同一用户多次赞助时，PHP 的「累计赞助金额」统计只留最后一笔。已对齐。
2. **`Qr::png()` 的静默区被渲染成深色**。位图以 0 为初值、浅色模块置位，
   于是"矩阵之外、从未写入"的像素全落成调色板 0 = 深色，二维码四周糊一圈黑边。
   **逐格比对矩阵永远发现不了**（静默区在模块矩阵里根本不存在），
   只有真解码才暴露。已改为「整行先铺浅色，再把深色模块的位清掉」。
3. **密集码模块像素过小**。版本 15 以上的码在 320px 目标下只分到 3–4 px/模块，
   实测 4 px 正是 OpenCV 检测器失败的临界尺寸（3/5/6/8/10 都能解，唯独 4 不行）。
   两端统一加最小模块像素 `6`（`Qr::MIN_MODULE_PX` / Python 的 `max(6, …)`）。
4. **非法金额返回 FastAPI 的英文 422 报文**：`amount=abc` 原本回
   `[{"type":"float_parsing","loc":["body","amount"],…}]`。三个端点改成用字符串
   接收、服务端解析（`_parse_amount` / `Sponsor::parseAmount`），
   现在回「金额必须是数字」。PHP 侧同理 —— `(float)"abc"` 会静默变 `0.0`
   然后报出"金额不能低于 1"这种指错方向的信息。
5. **`cross_check` 两条警告互相覆盖**（见 §2 的 `elif`）。

## 9. 教训

- **"后台能配、前台看不见"是一类静默失效**：`sponsor.pay_qr` 配了两年没人发现没生效，
  因为没有任何一处会报错。新增设置项时要顺手确认"它到底在哪个页面被读"。
- **"码图逐格正确" ≠ "能扫出来"**：静默区、模块像素尺寸这两个问题都只存在于
  "矩阵之外"，只有端到端把图交给真实解码器才会暴露。
- **`git reset --hard` 之后必须确认服务真的重启在文件落盘之后**：
  这一轮实测遇到 `main.py` 的 mtime 晚于服务启动时间（19:30:55 > 19:29:30），
  结果是"重启了、但跑的还是旧代码"，一条据此得出的结论全是错的。
  判据不能只看 `systemctl is-active`，要看**运行态**（如 OpenAPI schema / 接口行为）。
- **`(float)"abc"` 在 PHP 里静默变 0**：错误信息会指向完全错误的方向
  （"金额不能低于 1"而不是"金额必须是数字"）。

## 10. 附带事故与加固：`make_admin.php` 差点把生产 admin 抹掉

### 事故

验证 PHP 侧时，我在服务器上顺手跑了一次

```bash
php php/scripts/make_admin.php          # 没带任何参数
```

这个脚本的默认参数是 `admin` / `AdminPass123`，而它默认连的就是**生产库**
（`Db::pdo()` → `<root>/users.db`）。它的实际行为是：

```php
Kwrt\Db::run('DELETE FROM users WHERE username=?', [$user]);
Kwrt\Db::run('INSERT INTO users(username, password, email, created, role, sponsor, disabled, quota, email_verified) ...');
```

—— 也就是**先删后建**。后果：生产 admin 账号被当场删除重建，
口令变成 `AdminPass123`，`email` / `quota` / `sponsor_until` / `sponsor_tier` /
`sponsor_amount` / `created` 全部被覆盖成初始值。

### 恢复

用 2026-09-27 的库备份逐字段还原（`/root/_kwrt_bak_20260927-170145/users.db`），
口令用应用自身的 `_hash_pw()` 重新生成（保证 `pbkdf2_sha256$240000$盐$哈希` 格式与轮数一致）：

| 字段 | `make_admin` 覆盖后 | 还原为 |
|---|---|---|
| `password` | `AdminPass123` | `ThyxhuYFG7@ifcd`（`_verify_pw` 返回 True） |
| `email` | `admin@example.com` | `NULL` |
| `quota` | 50 | 12 |
| `sponsor_until` | `NULL` | `1793077358.367939` |
| `sponsor_tier` | `''` | `月付赞助` |
| `sponsor_amount` | 0.0 | 4.99 |
| `created` | 被刷新 | `1790414440.709941` |
| `id` | 2（自增新行） | 1 |

还原后实测：登录 200、`/api/v1/user` → `{logged_in:true, is_admin:true, sponsor_tier:'月付赞助'}`。

### 加固

这颗雷必须拆掉，否则下次还有人踩。`make_admin.php` 现在有三道闸，
任何一道不满足就在**碰数据库之前**退出（`exit 2`）：

1. **不允许"默认管理员口令"** —— 必须显式给出用户名与口令；
2. **不允许默认落到生产库** —— 必须显式设置 `KWRT_DB`；
3. **看着像生产库就再要一次确认** —— `KWRT_DB` 形如 `.../users.db` 且不在
   `tmp/test/fixtures` 目录下时，必须再加 `--i-know-this-is-destructive`。

实测（线上）：

```
1. 无参数                                   → 拒绝执行：必须显式给出用户名与口令。       exit=2
2. 只有用户名                               → 拒绝执行：必须显式给出用户名与口令。       exit=2
3. 用户名+口令，但没设 KWRT_DB              → 拒绝执行：未设置 KWRT_DB。                exit=2
4. KWRT_DB=/root/kwrt-clone/users.db        → 拒绝执行：KWRT_DB 看起来是**生产库**。     exit=2
5. KWRT_DB=/tmp/guard_test.db               → 已创建管理员 tester / pw123               exit=0
```

### 教训

- **"仅测试用"写在注释里，挡不住任何人。** 脚本名（`make_admin` 听起来像"创建"，实际是"删除+重建"）、
  默认参数（默认口令！）、默认连库（生产库！）三者合起来就是一个必然会被踩的坑。
  要挡就得用**代码**挡，不是用文档挡。
- **销毁性脚本的默认值必须是"拒绝运行"**，而不是"用最方便的参数运行"。
