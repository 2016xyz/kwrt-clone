# 构建失败的真正原因：10.7% 的设备上游根本编不出来

**用户报的现象**：「请稍后重试或更换软件包组合。构建失败」

**结论**：这不是「重试」能解决的问题。你选的 **JDCloud RE-CS-02 AX6600**
（`qualcommax/ipq60xx/jdcloud_re-cs-02`）**不在上游官方 ImageBuilder 里**，
本站的在线编译永远编不出它。而且范围远不止这一台 ——
**站点收录的 997 台设备里，107 台（10.7%）都是这种情况。**

顺带查出并修掉两个真缺陷：失败原因被前端丢掉；并发已满时再提交构建直接 **500**。

> 本报告不含任何明文凭据。

## 一、你那次失败的真实原因

从 GitHub Actions 的 run 日志里取到的原文（run #16，job 日志）：

```
Profile "jdcloud_re-cs-02" does not exist!
Use "make info" to get a list of available profile names.
make[1]: *** [Makefile:323: _check_profile] Error 1
make: *** [Makefile:355: image] Error 2
##[error]Process completed with exit code 2.
```

**注意这不是 GitHub 配置的问题，也不是软件包组合的问题。** 上游链路其实全通了：

```
版本解析     25.12 → 25.12.5                        ✓
ImageBuilder 可达检查  HTTP/2 200                    ✓
下载并解压    43.4M                                  ✓
注入 uci-defaults（主机名/LAN/PPPoE/无线）            ✓
编译固件      make image PROFILE=jdcloud_re-cs-02 …  ✗ Profile does not exist
```

也就是说：**只有「这个机型官方不认识」这一件事失败了**。

### 为什么官方不认识它

| | |
|---|---|
| 站点设备库 | `data/json/v1/releases/25.12/targets/qualcommax/ipq60xx/jdcloud_re-cs-02.json`，标题 `RE-CS-02 AX6600`（vendor `JDCloud`），预编译文件名前缀 `kwrt-09.18.2026-…` |
| 上游 `profiles.json` | `qualcommax/ipq60xx` 只有 **15** 个 profile，**一个 jdcloud 都没有** |

站点设备库来自 **kwrt 数据集**（kiddin9 那套自定义构建），
而本站在线编译用的是**上游官方 ImageBuilder**（`config.json` 的三个镜像全是
`downloads.openwrt.org` / 交大 / 阿里）。两者能覆盖的机型范围本来就不一样。

## 三、为什么那句文案是误导

```
web/index.html:681
    <b>构建失败</b><br>{{ job.error || '请稍后重试或更换软件包组合。' }}
```

`job.error` 在整个前端**从未被赋值**（全仓库只有这一处出现 `.error`）。
后端把失败原因写在 **`stderr`**：

```python
# app/backends.py::_await_completion
return {"status": "failed", "stdout": "", "stderr": logs,
        "detail": f"gh-{concl}", "external": True, "gh_run_url": ...}
```

所以真实原因**每次都被丢掉**，用户永远只看到那句兜底文案。
而它的两个建议**都不会成功**：

- 「重试」—— profile 不会因为重试而出现在上游 ImageBuilder 里；
- 「更换软件包组合」—— 软件包与 profile 是否存在毫无关系。

真正该说的是「换设备」或「去下预编译镜像」。这属于**把人往错方向带**，
比不给建议更糟。

（顺带：`job.log_tail` 同样从未赋值，所以那块「查看日志尾部」是死代码。）

## 四、顺带修掉的真 bug：并发提交 500

写回归测试时，用假镜像站让预检可测，结果意外撞出另一个真缺陷：

```
File "app/builder.py", line 772, in _pump
    job["queue_position"] = pos
UnboundLocalError: cannot access local variable 'job' where it is not associated with a value
```

原代码：

```python
while running < self.concurrency and not self.q.empty():
    jid = self.q.get()
    job = self.jobs.get(jid)          # ← job 只在 while 进循环时被绑定
    ...
# 刷新队列位置
pos = 0
for j in self.jobs.values():
    if j["status"] == "queued":
        job["queue_position"] = pos   # ← 循环变量是 j，却写到 job
        pos += 1
```

两种翻车：

1. **`UnboundLocalError` → 接口 500**：并发已满或队列空时 `while` 一次都没进，
   `job` 从未绑定。**线上 `builder.max_concurrent` 正是 1** ——
   等于「别人在编的时候你别点」，点了就 500。
2. **排队位置全错**：即使进了 `while`，位置也全写到刚启动的那个任务身上，
   真正排队的任务拿不到位置。

**PHP 版没有这个问题** —— 它用数据库队列 + 原子抢槽
（`UPDATE jobs SET status='running' WHERE request_hash=? AND status='queued'`），
位置用 `SELECT COUNT(*) FROM jobs WHERE status='queued'` 算，压根没有这层变量。
所以这是 **Python 独有**，只改 Python 侧。

## 五、修法

### 5.1 提交时预检 profile（`app/builder.py` + `app/main.py`）

新增 `builder.imagebuilder_profiles(release, target)`：拉上游 `profiles.json`
取该 release/target 真正支持的 profile 名集合，带 6 小时缓存 + 负缓存。

三处设计要点，都是踩过才知道的：

1. **必须用 `pick_version()` 走与真实构建同一条解析路径。**
   勾选仅第三方 feed 提供的插件时，`pick_version()` 会把版本从 25.12.5
   **回落到 24.10.8**（因为那些插件只在那条 feed 里）。profile 得在
   **那个 release** 里存在才算数；直接用 `req["version"]` 会误判。
2. **取不到 `profiles.json` 时放行**（返回 `None`）。
   这是「提前告知」，不是准入控制 —— 镜像站抖动/超时不该把正常构建拦掉。
   同时做负缓存，避免网络不通时每次都白等一轮 20 秒超时。
3. **拦截文案必须可行动** —— 说清是哪台设备、哪个平台、有多少替代，
   并指向预编译镜像，而不是「请重试」。

### 5.2 失败原因真的显示出来（`web/index.html`）

```diff
-<b>构建失败</b><br>{{ job.error || '请稍后重试或更换软件包组合。' }}
+<b>构建失败</b>
+<pre>{{ job.stderr || job.error || job.detail || '（后端未返回失败原因）' }}</pre>
+<a v-if="job.gh_run_url" :href="job.gh_run_url" target="_blank">在 GitHub 查看完整日志</a>
```

顺带删掉那块从未渲染过的「查看日志尾部」（`job.log_tail` 从未赋值）。

### 5.3 修 `_pump`（`app/builder.py`）

```diff
 for j in self.jobs.values():
     if j["status"] == "queued":
-        job["queue_position"] = pos
+        j["queue_position"] = pos
         pos += 1
```

## 六、验证

### 6.1 回归 `tools/verify_profile_guard.py`（8 项）

难点是「既要真验证，又不能烧 CI、不能跑几十分钟的重构建」。
做法：**自建一个假镜像站**，临时实例的 `imagebuilder_mirrors` 指向它：

- `25.12.5` 的 `profiles.json` → 返回**真实上游数据**（预检正常工作）
- 其它版本 → 404（用来制造「取不到」→ 验失败放行）
- ImageBuilder tarball → 一律 404（万一有构建漏过去，也只会立刻失败）

配合 `builder.backend=local`，全程不碰 GitHub。

```
  PG-1  编不出的设备被提前拒绝（jdcloud_re-cs-02）      ✓ HTTP 400 code=PROFILE_UNSUPPORTED
  PG-1b 拒绝原因可行动（含平台名与可编数量）              ✓ …该平台可在线编译的设备共 15 个
  PG-4  文案不再出现误导性话术                        ✓ 无「请稍后重试」等字样
  PG-2  能编的设备正常受理（x86/64/generic）           ✓ HTTP 202（证明不是一律拒绝）
  PG-3  profiles.json 取不到时放行                    ✓ HTTP 202（旧版本镜像不可达 → 放行）
  PG-7  并发已满时再提交不再 500                       ✓ HTTP 202
  PG-5  前端失败块引用 stderr                         ✓
  PG-6  接线守卫：build_post 真的调用了预检              ✓
  ──────────────────────────────────
  合计 8 项，全部通过 ✓
```

**已实测能报红**：把三处改动注入回去（`job["queue_position"]`→`job[…]`、
预检短路、前端改回读 `job.error`）→ **PG-1/1b/2/3/5/7 六项变红**；还原 → 全绿。

> ★ 套件里记下一个**我自己踩的坑**：假镜像 URL 必须带 `{version}`/`{target}`
> 占位符（app 的约定，`config.json` 里三个真实镜像都长这样）。
> 第一版我写成裸地址 `http://127.0.0.1:PORT/`，程序拼出来的是 `/profiles.json`
> → 404 → 预检失败放行，于是把「我的测试写错了」误判成了「产品有问题」。
> 差点就去改一段本来就是对的代码。

## 七、那 107 台设备的出路

预检只是把「假失败」变成了「真说明」，**没有让它们变得可编译**。
要真正支持，有三条路，按性价比排：

### 选项 A（推荐，改动小、立刻可用）：把在线编译按钮对这批设备关掉

既然上游编不出来，就别提供这个入口。做法：用同一套 `imagebuilder_profiles()`
在前端（或 `GET /api/v1/site` 下发一份清单）判断，对这批设备：

- 隐藏/禁用「自定义构建固件」整块；
- 在显眼处说明「该机型仅提供预编译镜像下载」。

**成本低、不会骗用户**，而且我已经验证了：这批设备的**预编译镜像都在**
（你选的那台有 3 个文件：`rootfs.tar.gz` 55.4 MB / `factory.bin` 49.5 MB /
`sysupgrade.bin` 48.3 MB），下载可用。

### 选项 B：接一个能覆盖 kwrt 机型的 ImageBuilder 源

站点设备库来自 kwrt 数据集，那批机型是 **kwrt 自己加的自定义 DTS**。
如果 kwrt/kiddin9 发布过对应的 ImageBuilder 产物（或提供可复现的构建源），
把它加到 `config.json` 的 `imagebuilder_mirrors` 里，这批设备就能真编了。

**目前没有据可依**：我在仓库文档与数据集里都没找到此类源的线索
（`config.json` 里三个镜像全是上游官方）。要做这条得先确认那个源**存在且稳定**，
属于待调研项，不能凭猜写进去。

### 选项 C：什么都不做，就靠现在这个提前拦截

现在已经是「点下去立刻说明为什么不行」，不会白等一轮 CI。
但用户仍会以为「也许能编」，体验不如选项 A。

### 你现在可以怎么做

想编那台 JDCloud RE-CS-02 AX6600，**用预编译镜像**；
若一定要自定义构建，把设备换成该平台上游支持的 15 台之一
（`8devices_mango-dvk`、`glinet_gl-ax1800`、`linksys_mr7350` …）。

## 八、没有做的事

- **没有为那 107 台设备找到真实可用的构建源。** 我只确认了「上游编不出来」，
  并让站点如实告知。选项 B 需要先确认 kwrt 侧是否存在稳定的 ImageBuilder 源。
- **没有在前端逐台标注「不支持在线编译」。** 那是选项 A，属于产品决策，
  等你定方向再落地 —— 后端拦截已经生效，不会误导或白等。
- 本轮没有派发任何构建到 GitHub（线上验证全程用的是会被提前拒绝的路径）。
