## 三、实测查明的真因

不是代码问题，是**环境装错了**：解释器是 Python 3.9，
而依赖里装着只支持 Python 3.10+ 的版本。实测到的几种真实报错原文：

```
ImportError: cannot import name 'TypeAlias' from 'typing'
TypeError:   unsupported operand type(s) for |: 'type' and 'NoneType'
SyntaxError: invalid syntax
```

**关键对照实测**：同样的 Python 3.9，用 `requirements.txt` 安装就没问题 ——
pip 会解析出兼容版本（fastapi 0.128.8 / uvicorn 0.39.0），

```
$ KWRT_PYTHON=/tmp/py39venv/bin/python PORT=8455 ./run.sh
{"ok":true,"jobs":0,...}                       ← healthz
/                        HTTP 200
/packages/               HTTP 200
/login/                  HTTP 200
/api/v1/site             HTTP 200
/manifest.webmanifest    HTTP 200
/robots.txt              HTTP 200
```

所以 README 写的「Python 3.9+」**是准确的** —— 错的是安装方式，不是版本要求。

---

## 四、`run.sh` 的三个缺陷

| # | 缺陷 | 后果 |
|---|---|---|
| 1 | 只比**版本号**，不做能力探测 | 3.9 版本号达标，但包装错了照样起不来 |
| 2 | 探测失败信息被 `2>/dev/null` 丢掉 | 只剩裸 traceback，用户无从下手 |
| 3 | **修复命令本身有害**：`pip install fastapi uvicorn`（无版本约束） | 旧 pip 会把最新版装进旧解释器 —— **大概率正是造成这个环境的操作** |

第 3 条尤其值得记：脚本一边报错，一边给出会**再次造成同样错误**的修复建议。

---

## 五、修复

### run.sh —— 换成「能力探测」

```sh
pick_python() {
  for c in "${KWRT_PYTHON:-}" python3 python3.13 python3.12 python3.11 python3.10; do
    command -v "$c" >/dev/null 2>&1 || continue
    "$c" -c "import fastapi, uvicorn" >/dev/null 2>&1 && { printf '%s' "$c"; return 0; }
  done
  return 1
}
```

- **真的 import 一次**，成功才算数 —— 版本号达标但包装错了会被这一步挡下；
- 候选顺序让脚本在「默认解释器坏了、旁边有能用的高版本」时**自己找到活的**；
- 启动改用探测结果（`exec "$KWRT_PY"`），不再写死 `python3`；
- 失败时**逐个解释器列出实测结果**（版本号 + 真实报错）。

### install.sh —— 装完必须证明能导入

此前只看 pip 退出码。pip 报成功但版本不兼容时，问题会推迟到第一次启动才爆。
现在追加导入校验，判据与 `run.sh` 保持一致。

## 六、★ 归类判据被实测推翻过一次

我最初按**猜想**写匹配规则，把

```
ImportError: cannot import name 'TypeAlias' from 'typing'
```

误判成「依赖没装」—— 那会把用户引向**重装依赖**（解决不了），而不是换解释器。

实测后改成：

| 错误特征 | 判定 | 含义 |
|---|---|---|
| `unsupported operand type` / `SyntaxError` / `from 'typing'` / `from 'types'` | `version` | 版本与解释器不兼容 |
| `No module named 'X.Y'`（**带点**） | `version` | 子模块缺失 = **已装但坏** |
| `No module named 'X'`（不带点） | `missing` | 一级依赖**真没装** |

**「带点的缺失」几乎总是「装了但不兼容」，不是「没装」** —— 这条区分是实测出来的。

`run.sh` 确实使用探测到的解释器；**并用实测到的 5 条真实报错原文验证归类判据**。

端到端真跑三种情形：

1. **Python 3.9 + requirements.txt** → 全部页面 200（见上）
2. **本机正常环境** `./run.sh` → healthz ok、页面 200
3. **影子 PATH 模拟「全部解释器不可用」** → 打印逐解释器诊断并 `exit 1`，
   **不再出现裸 traceback**

测试残留（3.9 venv、影子 PATH、强制装坏版本的 venv）已全部清理。

## 八、边界与未验证

1. **用户那台机器的完整堆栈无法在本机逐字复现** —— 本机 3.9 的 site-packages 里
   并没有 fastapi/uvicorn。但缺陷类别与修复方向由上述实测确定，
   `run.sh` 现在会把真实错误原样打出来，下次遇到可直接给出准确结论。
2. **`install.sh` 的完整流程未在真实 3.9 机器上重跑** —— 只对新增的校验分支
   做了针对性验证（好环境通过 / 缺依赖诊断 / 版本不兼容诊断三种情形）。
3. **`uvicorn/main.py` 内部那一帧的具体抛点未定位** —— 需要用户机器上的完整堆栈。
   不过已不影响使用：归类逻辑不依赖那一帧。
