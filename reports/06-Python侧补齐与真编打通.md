## 二、两个真实漏洞（Python 版，均已实测复现并修复）

### 2.1 `X-Forwarded-For` 可绕过封禁

```python
# 修复前
def client_ip(request):
    fwd = request.headers.get("x-forwarded-for")
    if fwd:
        return fwd.split(",")[0].strip()      # ← 客户端完全可控
    return request.client.host
```

该头由客户端完全控制。攻击者发 `X-Forwarded-For: 9.9.9.9` 即可任意换身份，
**封禁（`bans` 按 IP）与限速（登录锁定 / 注册限速）同时失效**。

**实测复现**（封禁 `127.0.0.1` 后）：

```
无伪造头          → 403 该来源已被管理员封禁
伪造 XFF=9.9.9.9  → 200 登录成功          ← 封禁被绕过
```

**修法**：只在「直连对端本身落在可信代理网段内」时才采信转发头，
并右往左跳过可信代理取第一个不可信地址；否则一律以 `REMOTE_ADDR` 为准。

### 2.2 `Host` 注入可污染邮件链接

`_site_base_url()` 采信 `x-forwarded-host` / `host`，而两者都由客户端控制 →
**发给用户的邮件里出现指向攻击者域名的链接**（钓鱼 → 账号接管），
支付宝 `notify_url` 也能被劫持。仅校验「格式合法」挡不住。

**修法**：只认 绑定域名 / 白名单内的 Host。

## 三、★ 关键发现：反向代理层会「抢先替你做决定」

**只改应用层是不够的。** 我修完上面两个漏洞后重测，**伪造头仍然能绕过封禁**。
原因是那层反向代理（此处为 ASGI 服务器）的默认行为：

```
proxy_headers          = True          # 默认开启
forwarded_allow_ips    = "127.0.0.1,::1"   # 默认值
```

只要直连对端是本机（**本机跑 nginx 是极常见的部署**），它就会
**在应用代码之前**用 `X-Forwarded-For` 改写 `request.client` ——
于是应用层再也分不清「真实对端」和「伪造的客户端」，
`app/netcfg.py` 里那套可信代理判定被**完全架空**。

**对照实测**：

| 配置 | 伪造 XFF 的结果 |
|---|---|
| 仅改应用层 | **200（被绕过）** ✗ |
| 再把 `forwarded-allow-ips` 置空 | **403（被拒）** ✓ |

已写进 `run.sh`（默认带、留空）与 `install.sh` 的 systemd unit，README 有专节说明。

> **教训**：做「信任边界」类修复时，必须确认**信任边界在哪一层**。
> 如果框架/服务器已经在更早的层替你做了信任判定，应用层的判定就是死代码 ——
> 而且它看起来是对的，测试也可能「通过」（如果测试没覆盖到那条路径）。

## 五、本轮修掉的自身缺陷（4 个）

| # | 缺陷 | 后果 | 修法 |
|---|---|---|---|
| 1 | `Engine` 缓存查找漏了版本号 | 前缀永远匹配不上 → 每次重复下载 46 MB | 用与 Python 侧逐字一致的命名规则 |
| 2 | **`proc_get_status()` 会消费退出码**，之后 `proc_close()` 返回 -1 | 编译**成功**了（镜像都产出了）却被判成「编译失败」—— 构建平台最怕「明明成功报失败」 | 退出码从 `proc_get_status()` 取 |
| 3 | `Router` 按**整串长度**排优先级 | `/dl/{path:path}`(14) 盖掉 `/dl/t/{token}`(13) → 令牌下载全被 302 到上游，表现为 403 | 改为按**字面量长度**排序 |
| 4 | 静态缓存头用 `setdefault` | 改不掉既有静态处理已写的 `no-cache` → 接了 CDN 仍每次回源，命中率永远 0 | 改为赋值覆盖 |

另为可排查性：`Engine` 增加过程日志（`work/<hash>/engine.log`），
且**「收集数为 0 时保留 `work/`」** —— 否则「构建成功却没产物」会连现场一起丢掉。
第 2 条正是靠它的上一版（保留现场的动机）才得以定位。

1. **【未验证】`sha256sums` 校验**：本次收集清单里没有 `sha256sums` 文件 ——

2. **【未验证】上传自定义文件包**（`tar.gz` 注入 rootfs）未在真编中验证 ——
   需赞助账号 + 一次完整构建。
3. **【需确认】`forwarded-allow-ips` 的生产取值**：若前面确有 CDN/反代，
   应把它设成其回源网段，并与后台「可信代理 / CDN 网段」**保持一致**。
   两处不一致会导致判定结果与预期不同。
4. **【需确认】PHP 版是否也有同类「上层抢先决定」问题**：
   PHP 走 `REMOTE_ADDR`，不带内置的代理头解析，因此**不受此坑影响**；
   但若在 PHP-FPM 前面放了 nginx 并自行 set 了 `REMOTE_ADDR`，
   就等于把信任边界交给了 nginx —— 此时 nginx 配置必须自己剥掉客户端的
   `X-Forwarded-For`，否则同样可被绕过。**这一条请在真实部署时确认。**
