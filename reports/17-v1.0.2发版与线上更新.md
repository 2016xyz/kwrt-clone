## 一、版本号的三处真源

这个项目的版本号有**三个落点**，设计上以仓库根 `VERSION` 文件为唯一真源：

| 位置 | 作用 | 改前 → 改后 |
|---|---|---|
| `VERSION`（仓库根） | **真源**，PHP 直接读它 | `1.0.1` → `1.0.2` |
| `app/version.py` 的 `VERSION` | Python 读的常量 | `"1.0.1"` → `"1.0.2"` |
| `php/src/Version.php` 的 `FALLBACK` | 仅当 `VERSION` 文件不可读时回落 | `'1.0.1'` → `'1.0.2'` |

`tools/verify_round6.py` 的 **V-1** 断言「VERSION 文件与 `app/version.py` 一致」，
**V-4** 断言「PHP 读到同一个版本号」—— 三处若跑偏会被立刻抓住。

改后实测：

```
V-1  VERSION 文件与 app/version.py 一致   ✓  文件=1.0.2 代码=1.0.2
V-2  版本格式合法且从 1.0.1 起            ✓  v1.0.2
V-3  display() 带 v 前缀                  ✓  v1.0.2
V-4  PHP 读到同一个版本号（同源）          ✓  PHP=1.0.2
V-5  healthz 与 /api/v1/site 均返回版本   ✓
V-6  后台界面显示版本号                    ✓
合计 42 项，全部通过 ✓
```

> ★ `VERSION` 文件**必须带末尾换行**。第一次写入时没有换行（5 字节），
> 立刻用 `od -c` 核对发现，补成 `1.0.2\n`（6 字节）。
> 这类「文件看起来对、实际少一个字节」的问题，光看内容看不出来。

### 顺带修掉的过期文档示例

`docs/更新升级与完整性检查.md` 里 `v1.0.1` 是**示例输出**，跟着升到 `v1.0.2`；
同一文件里「这是 **1.0.1** 修掉的问题」是**历史陈述**，保留不动。

这条区分很重要：不是所有 `1.0.1` 都该改。改错历史陈述会让文档说谎。

## 二、线上部署

### 2.1 更新脚本的做法

线上是 git 部署，更新走 `/root/_kwrt_update.sh`（沿用 16 号报告验证过的流程）：

```
备份点 /root/_kwrt_bak_20260927-135608
  备份 config.json（服务器专属 host/port）、kwrt.env、INITIAL_ADMIN.txt、users.db
  整包兜底 appdir.tar.gz
拉取   git fetch origin main → 远端 HEAD e7642f5，待应用提交数 1
应用   git reset --hard e7642f5
还原   config.json ← 服务器专属版（host: op.2016xlx.cn, port: 80）
自检   导入 20 个模块；失败 0
重启   systemctl restart kwrt → active；/healthz 200
```

**为什么不能直接 `git pull`**：`config.json` 是唯一「已跟踪且被本地改过」的文件 ——
线上是 `host: op.2016xlx.cn, port: 80`，仓库版是 `0.0.0.0:8443`。
`reset --hard` 会覆盖它，所以必须**单独备份 → reset → 还原**。
（实测确认服务实际监听参数来自 systemd 的 `0.0.0.0:8443`，`config.json` 的 host/port
未被服务读取 —— 但保留它仍是正确做法，不能让运维配置被静默抹掉。）

### 2.2 一个差点导致误判的坑：curl 访问 127.0.0.1:80 必须带 Host 头

更新完成后第一次验收，我用 `curl -s http://127.0.0.1/` 检查首页有没有新代码标记，
结果 **0 个命中**：

```
你已是赞助用户: 0
id="orders"     : 0
构建摘要(旧)     : 0
```

「新标记没有、旧标记也没有」—— 这个组合本身就说明**取到的不是这个站点的页面**。
根因：不带 `Host` 头时 nginx 落到 `default_server`，返回的是**另一个 vhost** 的内容。

加上 `Host: op.2016xlx.cn` 后立刻正确：

```
首页字节数    : 50774
id=orders     : 1
我的订单      : 8
你已是赞助用户: 1
/api version  : v1.0.2
/healthz ver  : 1.0.2
```

**教训**：在共享服务器上验收，永远带上正确的 `Host` 头；
或者直连应用端口（`127.0.0.1:8443`，此时不需要 Host）。
断言「某个标记不存在」之前，先确认「另一个必然存在的标记存在」——
否则你证的不是「没更新」，而是「看错站了」。

### 2.3 部署链路全貌（已逐一核对）

```
浏览器 → op.2016xlx.cn:80
       → nginx vhost /www/server/panel/vhost/nginx/op.2016xlx.cn.conf
       → include .../vhost/nginx/proxy/op.2016xlx.cn/*.conf
           location ^~ /  →  proxy_pass http://127.0.0.1:8443
                             proxy_set_header Host $host
       → systemd kwrt
           WorkingDirectory=/root/kwrt-clone
           ExecStart=.venv/bin/python -m uvicorn app.main:app
                     --host 0.0.0.0 --port 8443 --forwarded-allow-ips=
```

`/www/wwwroot/op.2016xlx.cn/` 下只有宝塔建的占位页（`index.html` 917B、`404.html`），
**不是应用目录** —— 应用在 `/root/kwrt-clone`，经反代对外。
服务器上也没有第二份部署（不存在 PHP 版实例），所以这次只需更新这一处。

## 四、`1.0.1` 残留全仓扫描

改版本号最容易出的错是**漏改**。所以改完做了一次全仓扫描（48 个命中），逐条判定：

| 类别 | 位置 | 处置 |
|---|---|---|
| **历史陈述**（正确保留） | `README.md` 的「## ★ v1.0.1 新增」整节、「自 v1.0.1 起共 29 次提交」 | 保留 —— 它记录的就是 1.0.1 那一版 |
| **旧报告**（归档） | `reports/10`、`reports/14`、`reports/15`、`reports/16` 里的当时的版本号 | 保留 —— 报告是历史快照，改了就成篡改 |
| **测试基线**（故意用旧值） | `tools/verify_round6.py` 的 `V.VERSION >= "1.0.1"`（「从 1.0.1 起」） | 保留 —— 断言的是下界，不是当前值 |
| **版本比较用例**（故意用 `1.0.10`） | `tools/verify_update_check.py`、`app/update.py`、`php/src/Update.php` 里 `"1.0.10" > "1.0.9"` 的说明与用例 | 保留 —— 讲的是字符串比较的经典陷阱 |
| **阴性对照样本** | `tools/verify_php.py:526` 的 `"构建由 OpenWrt 官方 ImageBuilder 完成 · v1.0.1"` | 保留 —— 用来验证「页面不泄露运行时版本」，需要一个**不该被识别**的串 |
| **包版本号**（同形不同义） | `data/json/.../packages-25.12/*-index.json` 里的 `20260425-r3` 等 | 保留 —— 与程序版本无关，是 OpenWrt 包版本 |
| **示例输出** | `docs/更新升级与完整性检查.md` 的 `v1.0.1` 示例 | ✅ **已改** 为 `1.0.2` |
| **当前版本定义** | 三处真源 | ✅ **已改** 为 `1.0.2` |

**结论：无漏改。** 只有「示例输出」和「真源」两类该改，其余 46 处都是历史或基线。

判断依据不是「grep 到就改」—— 那样会把文档改成说谎。
