## 二、检查方法

`tools/verify_integrity.py` 分五层，都是机械可复跑的：

| 层 | 检查什么 | 覆盖 |
|---|---|---|
| L1 语法 | 每个文件能否被自己的解析器接受 | Python / PHP / Shell / JSON / JS(node --check) |
| L2 完整性 | 有没有被写坏或截断 | 混语言残留、heredoc 闭合、空实现、占位符、末行截断 |
| L3 自洽 | 引用的东西存不存在 | 模板、控制器方法、API 路径、**设置键**、函数 |
| L4 对称 | 两版接口是否一一对应 | 路由集合、设置 schema 同源 |
| L5 交付 | 关键文件与能力是否齐备 | 29 个关键文件、19 模板语法、5 邮件模板 |

## 三、查出并修复的 11 个缺陷

### 3.1 【最严重】支付沙箱开关失效 → 打真实生产网关

PHP 读的是 `pay.sandbox`，而 schema 里的键叫 **`pay.alipay_sandbox`**。
`Settings::bool` 读不到就取默认 `false`，于是：

> **管理员打开沙箱模式后，PHP 仍会连 `https://openapi.alipay.com`（生产网关）**
> —— 测试期就会产生真实订单。Python 侧一直用对，所以两版行为还不一致。

**实测修复**（反射直调真实代码路径，非照抄逻辑）：

```
沙箱=开 → https://openapi-sandbox.dl.alipaydev.com/gateway.do
沙箱=关 → https://openapi.alipay.com/gateway.do
```

### 3.2 其余「键名写错 → 功能静默失效」（4 条）

| 代码里写的 | schema 里正确的 | 后果 |
|---|---|---|
| `mail.username` | `mail.user` | **SMTP 认证用户名永远为空** → 任何需要认证的邮件服务器都发不出邮件；且不报「配置缺失」，只在连接阶段被拒，极难定位 |
| `mail.verify_enabled` | `mail.verify_register` | **邮箱验证在 PHP 版从未生效过**，注册后可直接登录 |
| `build.default_quota` | `default_quota` | 后台改配额不生效，永远取默认 12 |
| `pay.order_prefix` | `pay.alipay_subject_prefix` | 订单主题前缀永远用 KWRT，且两版订单标题不一致 |

**行为级验证**（不只是「键能读到」，而是功能真的变了）：

```
邮箱验证开关 关 → {"need_verify": false}
邮箱验证开关 开 → {"need_verify": true}
配额设置 7     → 读到 7
mail.user      → 读到 smtpuser01（旧键 mail.username 读到空）
```

### 3.3 路由层：接口存在性缺陷（2 条）

**① `/api/v1/admin/overview` 固定 500**

`routes.php` 指向 `AdminController::overview`，而类里只有私有的 `overviewData()`。

```
HTTP 500
PHP Fatal error: Uncaught RuntimeException:
    控制器方法不存在: Kwrt\Controllers\AdminController::overview
```

已补公开 `overview()`，返回结构与 Python 版**同构**（密钥类字段已掩码，实测无泄漏）。

**② PHP 的 robots.txt 宣告了一个 404 的 sitemap**

PHP 根本没有 `/sitemap.xml` 路由（Python 有），而自己的 robots.txt 里写着
`Sitemap: .../sitemap.xml` —— 等于对外宣告一个 404。已补，并同时补上
Python 有而 PHP 缺的三个历史 301 重定向：

```
/index.css        → 301 /assets/css/app.css
/index.js         → 301 /assets/js/app.js
/form-storage.js  → 301 /assets/js/common.js
```

### 3.4 幽灵键：被代码读取但不在 schema 里（2 条）

- **`registration_open`** —— 注册接口与 `/api/v1/announcement` 都在读它，
  schema 里却没有 → 永远取默认值，**管理员无从关闭注册**。已补进 schema，
  并与 `page.register_enabled` 明确区分：那个管页面可见性，这个管是否收人。
- **`site.base_url`** —— 两版一致读取的内部覆盖键，**有意**不进 schema。
  已在检查器里**显式登记并写明理由**，而不是让它无声放行 ——
  「键不在 schema 里」正是这类缺陷的唯一信号，一旦放行就会漏掉真错误。

### 3.5 顺带清理：不再把内部参数伪装成可配置

`mail.timeout`（连接超时，引擎参数非业务配置）、`build.upload_max_mb`
（两版一致硬编码 200 MB）、`builder.keep_workdir`(排障开关)
—— 这三个原本都读 `Settings`，会让人以为后台能调（实际永远取默认）。
已分别改为常量 / 常量 / 环境变量 `KWRT_KEEP_WORKDIR`。

## 四、检查器本身修掉的 4 处误报

> **一个会误报的检查比没有检查更糟** —— 它会让人开始忽略整份报告。

| 误报 | 原因 | 处置 |
|---|---|---|
| `Router.php 花括号不配` | 路由模式 `/dl/t/{token}`、正则、heredoc 里的括号 | **删掉该检查** —— 它想抓的截断由 `php -l` 必然抓到（括号不闭合就是语法错），纯噪音 |
| `Engine.php:__construct 空方法` | PHP 8 属性提升把赋值写在参数列表里 | 排除 `__construct`/`__destruct`/`__clone` |
| 24 处 `placeholder` | HTML 属性 `placeholder="..."` | 只扫源码目录，排除 `placeholder=` |
| `app/__init__.py 空文件` | 合法的包标记 | 允许 `__init__.py` 为空 |

## 五、为什么必须做「两版对照」

上述 11 条里有 **4 条**（overview、sitemap、sandbox、subject_prefix）会让
**两版对同一个设置表现出不同行为**。

这类缺陷的特征是：**单看任何一侧的代码都是"对"的**。

- 只看 PHP：`Settings::get('pay.sandbox', false)` 语法正确、逻辑正确、有默认值兜底；
- 只看 Python：`SS.get("pay.alipay_sandbox")` 同样正确。

只有把两边摆在一起、并对着**同一份 schema** 核对，才能看出一个键名写错了。
这就是 L3（设置键存在性）与 L4（路由/schema 对称）两层存在的意义 ——
它们不是"好看"，是唯一能发现这类问题的手段。
