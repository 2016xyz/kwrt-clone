## 二、设置项（站点设置 → 程序更新，6 项）

| 键 | 默认 | 说明 |
|---|---|---|
| `update.enabled` | 开 | 关掉则后台不显示检查入口 |
| `update.repo` | `2016xyz/kwrt-clone` | 更新源仓库（owner/repo） |
| `update.ref` | `main` | 没有 Release 时从哪个分支读 `VERSION` |
| `update.token` | 空 | 私有仓库必填；留空回落 `gh.token` |
| `update.include_prerelease` | 关 | 开启后 `-beta` / `-rc` 也算可用更新 |
| `update.cache_minutes` | 10 | 缓存时长（1–1440） |

> `update.repo` **留空时不会回落到 `gh.repo`** —— 那是「固件构建器」仓库，
> 和本程序自己的源码仓库是两回事。回落到它会让检查去比对一个无关仓库的版本号，
> 比出「有新版本」比查不出来更糟（管理员会照着指引去升级一个不相干的仓库）。

## 三、四个设计决定（都是踩过才写下的）

### 3.1 版本比较必须逐段转数字，不能按字符串

```python
"1.0.10" < "1.0.9"     # 字符串语义：True（错）
"1.0.10" > "1.0.9"     # 版本语义：True（对）
```

按字符串比会导致「发了 1.0.10，后台反而说已是最新」，而且**只在跨两位数时
出现**，随手测根本撞不上。所以 UC-1 把 11 条边界逐条钉死。

预发布后缀同理要**逐段**比，不能只判断「有没有后缀」：

```
1.0.0-beta.2  vs  1.0.0-beta.1
```

只判断有无后缀 → 两者被判为相同 → 开了 `update.include_prerelease` 的管理员
**永远看不到 beta.2**。这一点是**第一版实现里真实存在的缺陷**，被 UC-1 抓出来后
才按 semver 补全（数字段按数值、数字段排在字母段前、字母段按字典序、
前缀相同则段数少的更小）。两版逐条对齐，UC-2 用同一张边界表验证结果**逐项一致**。

### 3.2 失败绝不伪装成「已是最新」

| 情况 | 返回 |
|---|---|
| 仓库不存在 / Token 无权 | `status=error`，「仓库或分支不存在，或 Token 无权访问（HTTP 404）」 |
| Token 无效 | `status=error`，「Token 无效或权限不足（HTTP 401/403）」 |
| 速率用尽 | `status=error`，「GitHub API 速率已用尽；配一个 Token 可提到 5000 次/小时」 |
| 网络不通 | `status=error`，「连不上 GitHub：<原因>」 |
| 未配置仓库 | `status=error`，「尚未配置更新源仓库（后台 → 站点设置 → 程序更新）」 |

把「查不了」显示成「最新」= 让管理员错过安全更新。UC-5 专门断言
失败文案里**不出现**「最新」二字。

### 3.3 必须缓存，且缓存要跟配置绑定

GitHub 未认证请求每小时 **60 次**。反复点几下就会把限额打满，
**连固件构建派发一起挂掉**。所以结果落 `update_checks` 表。

> 为什么落库而不是进程内缓存：**PHP 每个请求都是独立进程**，进程内缓存等于没有。
> UC-10 用「两次独立请求命中同一缓存」证明它确实跨进程。

缓存里同时存了**配置指纹**（仓库 + 预发布开关）：

```python
if (payload and ts and (time.time() - ts) < cache_minutes() * 60
        and payload.get("repo") == repo()
        and bool(payload.get("prerelease")) == include_prerelease()):
```

> **这是现场实测踩到的缺陷**：把 `update.repo` 从 A 改成 B 之后，页面仍端出 A 的
> 「已是最新」。拿一个不相干仓库的结论去指导升级决策，比查不出来更糟。UC-18 守它。

### 3.4 后台只查不升

让一个网页按钮去覆盖**正在运行**的程序文件并重启自身，一旦中途出错就没人收得了场
（半更新的状态、数据库结构不匹配、启动失败后连后台都进不去）。
所以接口注释里写死了这条边界，检查完给出指引，升级按
`docs/更新升级与完整性检查.md` 手工做：

```
备份（数据库 + store/ + 配置）→ 拉取新版本 → 重启服务
```

接口是**只读**的：不发任何写请求、不落地文件、不重启服务，因此用 `GET`
（也因此不需要 CSRF）。

## 四、顺带修掉的两个真实缺陷

### 4.1 「接口有值、页面没接线」

后端 `/api/v1/admin/overview` 返回了 `update` 段，但 `admin.js` 的
`loadOverview()` 是**显式重建**一个新对象（把嵌套结构拍平成视图模型）：

```js
ov.value = { users: u.total || 0, …, conf: conf, backend: d.backend || {} };
//                                    ↑ 新加的 d.update 没有映射进来
```

结果：**按钮渲染出来了，但永远 `disabled`** —— 看着像「功能没做」。
这是本项目反复出现的缺陷类（此前「后台能改、代码不读」是同一族）。

**修法**：补上映射。**并且做成了常驻断言**：

```
UC-17  总览接口的字段都被前端视图模型接上   ✓  接口 12 字段，未接线=无；负向对照可报红=True
```

两个细节值得记下：

- **扫描范围必须是整个 `loadOverview` 函数体，不能只看视图模型字面量。**
  形如 `q = d.queue || {}` 的**解构赋值**同样算「接上了」—— 第一版只看字面量，
  把 `download` / `queue` / `sponsor` 三个误判成未接线（**假阳性**）。
  带假阳性的检查器比没有更糟，所以必须修掉。
- **带负向对照**：塞一个 `__definitely_not_wired__` 进去，检查器必须能报出来 ——
  否则这条断言就是个永远为真的摆设。已实测：删掉 `update` 接线立刻变红，还原即通过。

### 4.2 缓存不与配置绑定

见 §3.3。**现场实测**：改仓库后页面仍端出旧仓库结论。已修 + UC-18。

## 八、遗留

1. **GitHub 速率**：未配 Token 时每小时 60 次。生产环境建议在
   「站点设置 → 程序更新 → 更新源 Token」填一个只读 Token（或确认 `gh.token`
   已有），提到 5000 次/小时。当前线上回落到 `gh.token`，工作正常。
2. **只查不升**是有意为之（§3.4）。若确实需要「一键升级」，那属于**破坏性操作**，
   需要先确认再动手 —— 且必须先做备份与回滚预案。
3. 本程序仓库目前**没有 Release**，所以走的是「读 `VERSION` 文件」这条路径。
   若以后发版时打一个 `v1.0.2` 的 Release，后台会自动显示发布说明与链接
   （`/releases` 优先级高于 `VERSION` 文件）。
