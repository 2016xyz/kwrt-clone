## 一、已修复的问题

### 1. 🔴 run.sh `MISS` 变量未初始化（构建启动必崩）

**文件**: `run.sh` 第 8 行

**问题**: 循环中 `MISS="$MISS $p"` 引用了未声明的变量。在 `set -e` 下行为未定义，
在 `set -u`（install.sh 使用）下直接报错退出。这是构建无法启动的首要原因。

**修复**: 在循环前添加 `MISS=""`。

```diff
+MISS=""
 need_rpm="perl-FindBin ..."
 for p in $need_rpm; do rpm -q "$p" >/dev/null 2>&1 || MISS="$MISS $p"; done
```

### 2. 🔴 run.sh 只支持 RPM 系统

**文件**: `run.sh` 依赖检查段

**问题**: 只用 `rpm -q` 检查依赖包，在 Debian/Ubuntu 上：
- `rpm` 命令不存在 → 每个包都 append 到 MISS
- 或直接跳过检查 → 运行时缺 perl 模块、zstd 等导致构建失败
- 用户看到的报错是 `make` 阶段的晦涩错误，而非缺依赖

**修复**: 增加 `dpkg -s` 分支，对 Debian 系用对应包名检查，未识别的系统给出提示。

### 3. 🔴 管理员明文密码泄露到 Git

**文件**: `data/INITIAL_ADMIN.txt`

**问题**: 包含 `admin` 用户的明文密码 `b32e7ff4ed26b033`，已被 git 追踪。
任何 clone 此仓库的人都能直接登录管理后台。

**修复**:
- `git rm --cached data/INITIAL_ADMIN.txt`
- 将 `data/INITIAL_ADMIN.txt` 和 `kwrt.env` 加入 `.gitignore`
- ⚠ **建议**: 立即修改线上管理员密码，并用 `git filter-branch` 或 BFG 清除历史

### 4. 🟡 builder.py / main.py 文件句柄泄漏（5处）

**文件**: `app/builder.py`（4处）、`app/main.py`（1处）

**问题**: `json.load(open(...))` 和 `open(f, "w").write(...)` 未用 `with` 包裹，
文件描述符依赖 GC 回收。在高负载下 fd 线性增长，可耗尽系统限制导致进程级 DoS。

**修复**: 全部改为 `with open(...) as f:` 模式。

## 二、已有但需注意的问题

### 5. 🟡 10.7% 设备上游编不出来（已有拦截机制）

report 19 已详细记录：站点设备库来自 kwrt 数据集（997 台），
而构建使用上游官方 ImageBuilder，其中 107 台（10.7%）上游不支持。
代码中 `builder.imagebuilder_profiles()` 已实现提前拦截，
但需要确保 profiles.json 缓存正常工作。

### 6. 🟡 无 GitHub Actions workflow 文件

仓库中没有任何 `.yml`/`.yaml` workflow 文件。
config.json 配置了 GitHub Actions 后端（`backends.py` 的 `GitHubBackend`），
但缺少对应的 workflow 定义文件。远程构建功能需要在目标仓库中
创建 `build-firmware.yml` 接收 `workflow_dispatch` 事件。

### 7. 🟢 config.json `base_url` 为空

`site.base_url` 为空字符串。代码中 `netcfg.base_url()` 有降级逻辑
（从设置 → config → 请求 Host 推导），但邮件链接、支付回调等
依赖正确的 base_url。部署时必须填写实际域名。

## 三、代码质量评价

### 做得好的地方

1. **输入净化**: `app/params.py` 对所有构建参数做了严格的白名单校验，
   防止了命令注入（target/profile 进 shell/make 的场景）
2. **路径穿越防护**: `builder._safe_extract()` 和 `_inside()` 对归档解压
   做了完善的 Tar-Slip 防护
3. **CSRF 防护**: `main.py` 的 `_same_origin()` 中间件对写操作做了 Origin 校验
4. **IP 信任链**: `netcfg.py` 正确实现了可信代理网段判定，
   避免了 X-Forwarded-For 伪造绕过封禁
5. **fd 泄漏修复**: `dbutil.ClosingConnection` 优雅地解决了 SQLite 连接泄漏
6. **构建队列**: `BuildQueue._pump()` 的 TOCTOU 竞态已用 RLock 修复
7. **错误诊断**: `run.sh` 的 Python 解释器探测逻辑非常细致，
   能区分「版本不兼容」和「依赖没装」两种失败

### 架构亮点

- Python + PHP 双版本后端共用同一个 SQLite 数据库，可互相接管
- 本地 ImageBuilder + GitHub Actions 双构建后端，多队列轮转
- 第三方插件自动回落 opkg 后端（24.10），apk 后端（25.12）无缝切换
- 构建产物带限时下载令牌（HMAC 签名），支持 CDN 域名
